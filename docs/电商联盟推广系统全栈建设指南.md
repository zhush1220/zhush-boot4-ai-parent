## 第一部分：战略与技术选型

### 1. 系统对接策略

#### 1.1 核心目标

- **长期规模化运营**
- **对佣金成本敏感**
- **希望掌握用户数据**

#### 1.2 两种对接路径对比

| 对比维度       | 官方直连              | 第三方聚合接入（大淘客/好单库） |
| :------------- | :-------------------- | :------------------------------ |
| **开发成本**   | 高（需适配各平台API） | 低（统一接口封装）              |
| **成本结构**   | 无中间抽成            | 抽取部分佣金                    |
| **数据控制权** | 完全掌握              | 受限于聚合平台                  |
| **适用场景**   | 长期规模化运营        | 快速验证MVP                     |

#### 1.3 推荐方案

采用**官方直连为主，第三方聚合为备降**的双层策略：

- **主路径**：直接对接淘宝联盟、京东联盟、拼多多多多进宝官方API
- **备降路径**：当官方API限流或故障时，自动降级到大淘客等聚合平台

### 2. 系统架构设计

#### 2.1 架构演进策略

- **初期**：采用**高度模块化的单体架构**（Spring Boot多模块）
- **长期**：按**微服务蓝图**演进，预拆分推广网关、用户中心、商品推广、订单归因、佣金结算、数据报表等核心服务

#### 2.2 项目结构（基于zhush-boot4-parent）

```text
zhush-boot4-parent/
├── zhush-dependencies/        # 统一依赖管理
├── zhush-framework/           # 通用基础设施
│   ├── zhush-spring-boot-starter-mybatis
│   ├── zhush-spring-boot-starter-redis
│   ├── zhush-spring-boot-starter-mq
│   ├── zhush-spring-boot-starter-job
│   └── ...
├── zhush-module-union/        # 联盟推广业务模块（新增）
├── zhush-module-member/       # 会员模块
├── zhush-module-system/       # 系统模块
└── zhush-server/              # Web启动入口
```

## 第三部分：数据同步策略

### 1. 商品信息同步

- **实时查询**：先查Redis缓存 → 再查本地数据库 → 最后调用第三方API

- **定时批量同步**：利用定时任务（`zhush-spring-boot-starter-job`）在低峰期增量/全量同步

- **同步策略**：优先增量同步，每周一次全量刷新

  

### 2. 订单/佣金同步

- **被动推送**：接收平台订单推送，通过MQ异步处理
- **主动轮询**：配置定时任务轮询各平台订单API，保证不丢单
- **去重处理**：使用 `(platform, outer_order_id)` 唯一索引保证幂等性

## 第四部分：最终一致性保障

### 1. 本地消息表 + MQ可靠投递

订单接收后先写入本地消息表，再发送MQ，确保不丢单。

### 2. 幂等性设计

- 数据库唯一索引防重
- 业务层分布式锁（Redis）防并发

### 3. 分布式锁 + 乐观锁

账户余额更新使用 `SELECT FOR UPDATE` + `version` 乐观锁双重保障。

### 4. TCC分布式事务

跨服务（订单→佣金→账户）的场景，可考虑TCC模式。

### 5. 状态机驱动

佣金记录表使用状态机管理流转：待计算 → 待入账 → 已入账。

### 6. 定时补偿任务

每天凌晨运行对账任务，修复异常订单和佣金记录。

## 第六部分：关键业务逻辑优化建议

### 1. 外部推广者“重复入账”风险（P0）

- **问题**：`member_id` 和 `external_promoter_id` 可能同时存在
- **方案**：增加互斥校验，`promoter_type=1`时只能有`member_id`，`promoter_type=2`时只能有`external_promoter_id`

### 2. 账户余额并发更新（P0）

- **问题**：提现和佣金入账并发可能导致余额不一致
- **方案**：`SELECT FOR UPDATE` + 乐观锁 `version` 字段

### 3. 佣金计算日志缺失（P1）

- **问题**：无法追溯佣金计算过程
- **方案**：增加 `calc_snapshot` JSON字段，记录规则ID、各层级分配明细

### 4. 订单去重机制（P1）

- **问题**：MQ重复消费可能导致重复处理
- **方案**：以 `platform:outer_order_id` 为Key增加Redis分布式锁

### 5. 订单索引优化（P2）

- **问题**：`union_order` 表9个索引影响写入性能
- **方案**：合并 `order_status` 和 `settle_status` 为联合索引

### 6. JSON字段查询性能（P2）

- **问题**：风控规则中的JSON条件无法走索引
- **方案**：提取关键字段为辅助列（Generated Column）
