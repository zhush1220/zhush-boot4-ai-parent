## 一、行级数据权限（`DataScopeProvider` + `@DataPermission`）

### 1.1 现状盘点

**已接入：全仓 1 处。**

| 位置 | 注解配置 | 附加处理 |
| --- | --- | --- |
| `AdminUserService#getUserPage` | `@DataPermission(deptColumn = "dept_id", userColumn = "id")` | `DataPermissionHelper.ignore(() -> fillRoleIds(list))` |

`userColumn` 从默认 `create_by` 改为 `id` 是正确决策：`sys_admin_user` 的 `create_by` 恒为 NULL（系统内置账号非用户创建），沿用默认会让"仅本人"永远查不到自己。

**未接入统计（按模块）**

| 模块 | 对外查询方法数 | 已接入 | 接入率 | 是否依赖 starter |
| --- | --- | --- | --- | --- |
| `zhush-module-system` | 31 | 1 | 3.2% | 是 |
| `zhush-module-union` | 44 | 0 | 0% | **否** |
| `zhush-module-ai` | 15 | 0 | 0% | **否** |
| `zhush-module-member` | 1 | 0 | 0% | **否** |
| 合计 | **91** | **1** | **1.1%** | — |

system 模块未接入的 30 个方法按风险分层：

- **高敏（含人员/凭证/资金线索）**：`AdminUserService` 的详情与写操作（见 R-2）、`Oauth2ClientService#getClientPage`（clientSecret）、`AdminRoleService#getRolePage`/`listAllEnabled`、`AdminDeptService#listDepts`/`treeDepts`、`FileService#getFilePage`、`LoginLogService#getLoginLogPage`、`OperateLogService#getOperateLogPage`、`SqlAuditLogService#getSqlAuditPage`、`OpenApiLogService#getOpenApiLogPage`
- **中敏（配置类，通常应全局可见）**：字典类型/字典数据、岗位、定时任务、通知公告、菜单
- **无需接入（结构性）**：`AdminAuthService#getUserMenus`/`getAccessCodes`（本身按登录人派生）、`AdminPermissionService`（鉴权底座，接入会自锁）、`CacheMonitorService`/`DruidMonitorService`（非业务表，走 QueryWrapper 但无归属列，接入即 `Unknown column`）

**关键结构性约束：全库仅 `sys_admin_user` 一张表有 `dept_id` 列**（`01_admin_rbac.sql:25`、`09_union.sql:91`）。这意味着"本部门 / 本部门及以下 / 自定义部门"三档数据范围**当前只对 1 张表真正可用**；其余表只能落到"仅本人"（依赖 `BaseEntity.createBy`，由 `GlobalInsertListener` 自动填充，覆盖面好）。这是接入率低的技术根因，不是遗漏。

### 1.2 缺陷检测

#### R-1（P0，实测复现）OR 条件会静默短路行级过滤

`DataPermissionDialect:68` 用 `queryWrapper.and(condition)` 追加过滤条件。用 mybatis-flex 1.11.8 实跑渲染：

```
现状（业务 WHERE 含顶层 OR）
SELECT * WHERE `username` LIKE '%abc%' OR `mobile` = '13800000000' AND `dept_id` IN (1, 2)
                                                       ^^^ MySQL 优先级 AND > OR
等价语义： username LIKE '%abc%'  OR  (mobile = '13800000000' AND dept_id IN (1,2))
→ 第一个 OR 分支完全不受数据权限约束，越权返回全库数据，且无任何报错或日志。
```

尝试过的两种"看似正确"的修复均**实测无效**：

| 尝试 | 渲染结果 | 判定 |
| --- | --- | --- |
| `QueryMethods.bracket(cond)` 后 `and` | `... OR `mobile` = ? AND (`dept_id` IN (1, 2))` | ✗ 括号只包住 AND 右操作数，短路依旧 |
| 整条链交给 `where(chain)` | `... OR ... AND `dept_id` IN (1, 2)` | ✗ 顶层链不加括号 |

并且方言层**无法根治**：`QueryWrapper` 未暴露 where 链的 getter（`getDeclaredMethods` 中含 `where` 的仅 `where` 本身），拿不到已有条件就无法整体重包裹。

**当前是否已受害：否。** `getUserPage` 用 `QueryWrapperX.like/eq/eq`，全 AND 连接，渲染为
`... AND `status` = 1 AND `dept_id` IN (1, 2)`，语义正确。
**但 `QueryWrapperX` 继承自 `QueryWrapper`，`or(...)` 系列公开可用**，任何后续接入表只要写一个顶层 OR 就会静默失效——这是"接入即踩"的最高危陷阱。

**处置**：见第五章最小修复方案 M-1（约定红线 + 安全 API + 单测护栏，方言层不可根治已取证）。

#### R-2（P0）行级过滤只保护列表，详情与写操作可横向越权

`javap com.mybatisflex.core.BaseMapper` 取证：

```
public abstract T   selectOneById(java.io.Serializable);   // 不走 QueryWrapper
public abstract int deleteById(java.io.Serializable);      // 不走 QueryWrapper
public abstract int update(T, boolean);                    // 不走 QueryWrapper
public default int  update(T);                             // → 委派到上面的 abstract
public default T    selectOneByQuery(QueryWrapper);        // 走 QueryWrapper，会被过滤
public abstract List<T> selectListByIds(Collection);       // 不走 QueryWrapper
```

`prepareAuth` 只在 QueryWrapper 上触发，因此 `AdminUserService` 中
`getUser(id)` / `updateUser` / `deleteUser` / `deleteUserBatch` / `assignRoles` / `resetPassword`
**全部绕过行级数据权限**。实际后果：

- 仅拥有"本部门"范围的部门管理员，构造他人 ID 即可 `GET /admin/user/{id}` 读取全库任意管理员详情；
- 可 `PUT` 修改、`DELETE` 删除跨部门账号；
- 可 `assignRoles` 给任意账号（含超管账号本身）改角色，或通过 `resetPassword` 重置他人密码后登录 → **提权到超管**。

这是本次审计最高危项：列表挡住了，单条与写入没挡。列级权限只能减轻（mobile/email 被 CLEAR）**但不能阻止**越权读改。

**处置**：见最小修复方案 M-2。

#### R-3（P2，符合预期）`ignore()` 遗漏场景

问题「是否存在遗漏 `ignore()` 导致 `Unknown column` 的场景」——**当前无遗漏，且现有 `ignore()` 必要而非多余**：

- `fillRoleIds` → `SysAdminUserRoleMapper#selectListByUserIds` 是 `default` 方法，内部 `QueryWrapper.create()` + `selectListByQuery()` → **会被 `prepareAuth` 拦截**，而 `sys_admin_user_role` 无 `dept_id`/`create_by` 列 → 不包 `ignore()` 必报 `Unknown column dept_id`。当前包裹正确。
- 反向确认：`saveUserRoles` 里的 `roleMapper.selectListByIds(roleIds)` 是 abstract → 不被拦截 → **不需要** `ignore()`；若有人"顺手全包上"反而是噪音。
- `AdminDataScopeProvider#resolve` 内部查角色/用户/部门由方言层 `setIgnore(true)/finally setIgnore(false)`（`DataPermissionDialect:57-62`）保护，递归防护到位；`deptMapper.selectAll()` 在 ignore 窗口内执行，取证通过。
- `DataPermissionHelper.ignore` 保存并恢复 `boolean original`，嵌套调用语义正确，不存在内层 `setIgnore(false)` 提前解除外层保护的问题。

**真正的遗漏风险在"新增代码"而非"存量代码"**：任何在 `@DataPermission` 方法内新加的 `selectListByQuery`/`selectCountByQuery`/`selectPageX` 类调用都会中招。→ checklist 第 5 步给出判定表。

#### R-4（P1）缓存失效未覆盖全部数据范围变更路径

| 变更路径 | 失效调用 | 覆盖 |
| --- | --- | --- |
| `AdminRoleService#assignDataScope` | `invalidateAll()` | ✅ |
| `AdminRoleService#updateRole`（含启停） | `invalidateAll()` | ✅ |
| `AdminRoleService#deleteRole` | `invalidateAll()` | ✅ |
| `AdminUserService#updateUser`（归属部门变） | `invalidate(id)` | ✅ |
| `AdminUserService#deleteUser` | `invalidate(id)` | ✅ |
| `AdminUserService#assignRoles` | `invalidate(id)` | ✅ |
| **`AdminDeptService#createDept/updateDept/deleteDept`** | 无 | ❌ 靠 60s TTL |
| **角色-菜单分配 `assignRoleMenu`** | 无 | ⚠️ 不影响 `data_scope`，可接受 |
| **`AdminUserService#createUser`** | 无 | ⚠️ 新用户无缓存条目，无需失效，正确 |

部门维度未失效是**刻意的循环依赖规避**（见 3.3），代价是"部门挪动/删除后，`本部门及以下` 口径最迟 60s 生效"。属可接受权衡，但必须文档化——当前类注释只说了"角色调整最迟 1 分钟"，未提部门变更。

#### R-5（P1）进程内缓存无跨实例广播

`AdminDataScopeProvider.cache` 是本地 `ConcurrentHashMap`。`invalidateAll()` 在 docker/prod 多副本部署下**只清本节点**。表现为：在 A 节点调整角色数据范围并提示"已生效"，命中 B 节点的请求仍按旧范围过滤，最长 60s。
代码注释与文档中"主动失效，使调整立即生效"的表述在多实例下不成立，应修正为"**单实例立即生效，多实例最迟 60s**"。

#### R-6（P2，符合预期）超管与 NULL `data_scope` 处理

`resolve()`：`SUPER_ADMIN_CODE.equals(code) || dataScope == null || dataScope == 1` → `DataScope.all()`。

- `data_scope = 1`（全部）→ 不过滤 ✅
- `data_scope IS NULL` → 视为全部，兼容 `01_admin_rbac.sql` 存量行（该列后加且无默认回填），**不误伤存量数据** ✅
- **无任何启用角色 → `DataScope.self(userId)`（最小权限）** ✅ 不是 fail-open
- 无 `1/2/3/5` 而全为 `4` → `self` ✅
- 多角色 2/3/5 → 部门 ID 取并集（`LinkedHashSet`）✅
- 空指针防护：进入 `switch (role.getDataScope())` 前，`null` 已被 `hasAll` 短路返回，**拆箱安全**（这条容易被误读为缺陷，已取证确认无问题）
- 部门集合为空时由 `DataPermissionDialect#deptCondition` 退化为"仅本人"；userId 也为 null 时 `denyAll()` → `userColumn = -1` → 零结果 ✅ 不越权

**唯一语义待商榷**：`data_scope IS NULL` 当"全部"是宽松默认。存量兼容有必要，但新建角色走 `assignDataScope` 前若忘了设置，就默认全库可见。`sys_role.data_scope` 在 `09_union.sql:301` 已定义为 `NOT NULL DEFAULT 1`——默认值 1 也是"全部"。建议后续把新建角色默认改为 `4-仅本人`（P2，需产品确认，会影响存量运营习惯）。

#### R-7（P1）未登录即 `DataScope.all()`，行级过滤 fail-open

`getDataScope()`：`StpAdminUtil.getLoginIdDefaultNull() == null` → `DataScope.all()`。
设计意图正确（定时任务、MQ 消费、系统内部调用需要全量），但**无法区分"系统调用"与"未鉴权却调到业务方法"**。当前所有 admin Controller 均有 `SaCheckPermission` 前置，实际不可达；一旦新增免登录接口复用了带 `@DataPermission` 的 Service 方法，就会全库返回且不报错。
建议引入显式系统调用标记（如 `DataPermissionHelper.runAsSystem(...)` 内部才返回 all），默认未登录 → `denyAll`（P1，属纵深防御，非现网漏洞）。

### 1.3 扩展性评估

接入成本低但**约束前置**：表必须有归属列。行级接入的完整步骤清单见《[数据权限-行级业务表接入checklist.md](./数据权限-行级业务表接入checklist.md)》，其核心约定：

1. 表必备列：`dept_id`（部门维度）**或** `create_by`（仅本人维度），二者皆无 → 不能接入；
2. 注解参数：`deptColumn` 默认 `dept_id`、`userColumn` 默认 `create_by`，`sys_admin_user` 这类归属人即主键的表须显式改成 `id`；
3. `ignore()` 包裹规则：只对"被 `prepareAuth` 拦截且目标表无归属列"的调用包裹（判定表见 checklist 第 5 步）；
4. **OR 红线**：`@DataPermission` 方法内禁用顶层 `.or(...)`，OR 组必须 `QueryMethods.bracket(a.or(b))` 作为单个 AND 节点（实测安全写法已验证）。

### 2.2 缺陷检测

#### F-1（P2，选型正确）CLEAR vs MASK

当前三处全用 `CLEAR`，与业务形态匹配：`AdminUserVO` 同时服务列表与**编辑表单回填**，若用 `MASK` 会把 `"***"` 当真实值回填并可能被子表单提交覆盖 → **`MASK` 用于可回填字段是数据污染风险，`CLEAR` 是正确选择**。

选型规则（已写入列级 checklist）：

| 字段用途 | 正确策略 | 理由 |
| --- | --- | --- |
| 表单回填 / 可提交 | **CLEAR** | MASK 会把占位符当成用户输入写回库 |
| 只读展示（日志、详情） | MASK 可选 | 保留"有值但不可读"的 UI 提示 |
| 计数、状态等非展示数值 | CLEAR | MASK 对非 String 等同 CLEAR（见 F-2） |

**结论：选型逻辑正确，无缺陷。**

#### F-2：`FieldPermissionResponseAdvice` 边界审查

逐项取证，含 2 项真实缺陷：

| 机制 | 实现 | 判定 |
| --- | --- | --- |
| `MAX_DEPTH = 4` | `process()` 首行 `depth > MAX_DEPTH → return` | **F-2a：超限静默跳过 = fail-open**。深层嵌套 VO（第 5 层）上的 `@FieldPermission` 字段不会被处理，无任何告警。当前最深链路为 `Result → PageResult → VO → 嵌套 VO`（深度 3），未触发；但链路一旦加深即静默泄露 |
| `ANNOTATED_FIELD_CACHE` / `NESTED_FIELD_CACHE` | `static ConcurrentHashMap`，`computeIfAbsent`，含父类非 static 字段 | 正确。键为 `Class<?>`，条目数 = VO 类数，不无界增长。`declaredFields()` 已排除 static，`setAccessible(true)` 只在解析期一次。⚠️ 热部署/ClassLoader 场景会钉住旧 ClassLoader（P2，运维注意，非功能缺陷） |
| primitive 跳过 + warn | `applyStrategy()` 首行 `isPrimitive() → log.warn + return`（**保留原值**） | **F-2b：fail-open 且 warn 无去重**。①无权限时字段值原样输出，敏感 `long`/`int`（如金额、身份证后拼接的数值型）**泄露**；②`log.warn` 位于「每行 × 每字段」的内层循环，100 行/页即 100 条告警，无节流 |
| `MASK` 对非 String | `annotation.strategy() == MASK && field.getType() == String.class ? maskValue : null` | 语义正确（等同 CLEAR），但**无告警**，`@FieldPermission(strategy = MASK)` 标在 `Integer` 上静默变 null，前端拿到 null 而非占位符，容易误判为 bug（P2） |
| 异常处理 | `beforeBodyWrite` try/catch → `log.warn` 后原样返回 body | **F-2c：fail-open**。`Field.set` 抛异常（如 **record 组件字段为 final**、JDK 模块限制）时整批过滤中断，该响应所有敏感字段原样下发。当前 VO 均为 Lombok `@Data`（非 final 字段）未触发；**一旦有 VO 改用 Java record，列级权限会静默全失效** |
| `Map` 响应体 | `obj instanceof Map → return` | **F-2d：fail-open**。`Result<Map<String,Object>>` 返回的敏感值无法被纳管（无字段可注解）。`DruidMonitorService` 4 个方法即返回 `List<Map<String, Object>>`。需在 checklist 立红线：敏感数据禁用 Map 下发 |
| 集合递归 | `processCollection` 不增加 depth | `List<List<VO>>` 可绕过深度限制（P2，当前无此形态） |
| `supports()` 恒 `true` | 所有 ResponseBodyAdvice 场景都进入 | 功能正确（依赖 `isPlainType` 快速短路），但每个 HTTP 响应都过一遍；无 `@Order`，与未来其他 Advice 存在执行顺序不确定性（P2） |

#### F-3（P1）导出与非 JSON 响应是列级盲区

`LoginLogController#export` / `OperateLogController#export` → `void` + `HttpServletResponse` 输出流，**不经过 `ResponseBodyAdvice`**。列级权限对导出完全无效：一旦给 `LoginLogVO.loginIp` 加 `@FieldPermission`，页面看不到但 `/export` 能拿到全量 Excel。
当前实际泄露为 0（`AdminUserVO` 无导出接口，日志 IP 未纳管），属**机制性陷阱**。

#### F-4（P1）`PermissionChecker` 全局单 Bean，跨端口径冲突

`zhush-server/pom.xml` 依赖 starter → `FieldPermissionResponseAdvice` 在**整个应用**注册为 `@RestControllerAdvice`；`AdminPermissionChecker` 是唯一 `PermissionChecker`（`@ConditionalOnMissingBean`），口径为 `StpAdminUtil.isLogin() && hasPermission(...)`。

后果：**会员端（`uni`）请求若命中带 `@FieldPermission` 的 VO，判定必然为 false → 字段被清空**。这是 fail-closed（不泄露），但对会员是业务错误——`MemberUserVO.mobile` / `MemberInfoVO.mobile`（"我的"页展示本人手机号）一旦被标注就会永远为空。
故 **会员端 VO 禁止直接纳管**，须先把 `PermissionChecker` 改造为按会话类型路由（admin → `StpAdminUtil`，member → `StpMemberUtil`，未登录 → 拒绝）。这是本报告明确"暂不扩大到 member/union"的原因。

#### F-5（P2，已实测确认安全）通配符 `"*"` 匹配方向

Sa-Token 1.46.0 实跑（`SaStrategy.instance.hasElement`，签名 `(List<String> elements, String permission)`）：

```
hasElement(["*"], "system:user:mobile")  → true    // 权限集合含 "*" 时放行一切（超管语义）
hasElement(["system:user:*"], "system:user:mobile") → true  // 前缀通配
hasElement(["system:user:mobile"], "*")  → false   // 反向不匹配，用户不可能用 "*" 反查
```

判定：超管权限集合里的 `"*"` **只出现在 elements 位置**（由 `AdminPermissionService#getPermissionList` 为超管注入），普通用户权限列表不含 `"*"`。`vagueMatch(userPerm, "*") == false` 保证用户无法通过持有字面量 `"*"` 权限点反向绕过。
**结论：通配匹配安全。** 残余风险仅在于"把 `*` 授予非超管角色"，属授权配置纪律，非框架缺陷。

### 2.3 扩展性评估

列级机制**已具备跨模块复用条件**：注解 + 全局 Advice + 前端 `useFieldPermission` hook（`apps/web-antdv-next/src/hooks/use-field-permission.ts`，`ColumnConfig.permission` + `filterColumns`）+ SQL 幂等注册模板齐备。完整步骤见《[数据权限-列级业务表接入checklist.md](./数据权限-列级业务表接入checklist.md)》。

唯一硬门槛：**新模块必须是管理端口径**。会员端/小程序端接入前须先完成 F-4 的 `PermissionChecker` 路由改造。

## 三、整体架构与配置

### 3.1 总开关各 profile 状态与风险

| profile | `enabled` | `row-enabled` | `field-enabled` | 风险评估 |
| --- | --- | --- | --- | --- |
| `dev` | **true** | true | true | 无 |
| `docker` | **true** | true | true | 无 |
| `prod` | **true** | true | true | 无 |
| `test` | **false** | 注释 | 注释 | ⚠️ **测试环境不启用 → 数据权限行为在集成测试/验收阶段完全不被覆盖**，只有单测护栏。这是当前配置的最大风险点：R-1/R-2 这类缺陷在 test 环境跑不出任何异常 |

其他：

- `DataPermissionProperties` 无默认 `enabled=true`，`@ConditionalOnProperty(... havingValue="true")` **无 `matchIfMissing`** → 未配置即整体关闭，对未接入环境零侵入。✅ 正确的安全默认。
- 三级开关（总/行/列）装配已被 `DataPermissionAutoConfigurationTest` 7 例覆盖（默认关闭无 Bean、开关组合、默认 SPI 全放行、业务 SPI 覆盖）。✅
- 子开关默认 `matchIfMissing = true`，即只写 `enabled: true` 就两档全开——需注意"只想开列级不想开行级"时必须显式写 `row-enabled: false`。

### 3.2 方言覆盖安全性（MySQL `CommonsDialectImpl` 等价性取证）

`DataPermissionAutoConfiguration:80` 执行 `DialectFactory.registerDialect(DbType.MYSQL, dataPermissionDialect)`，这是**全局静态注册**，会替换掉 mybatis-flex 默认的 MySQL 方言。风险在于替换后分页/引号行为是否改变。取证：

```
反射调用 DialectFactory.createDialect(DbType.MYSQL)
default MYSQL dialect impl = com.mybatisflex.core.dialect.impl.CommonsDialectImpl
  chain: com.mybatisflex.core.dialect.impl.CommonsDialectImpl
  chain: java.lang.Object
```

即 mybatis-flex 1.11.8 的默认 MySQL 方言**就是 `CommonsDialectImpl` 本身（无子类）**；
`DataPermissionDialect extends CommonsDialectImpl(KeywordWrap.BACK_QUOTE, LimitOffsetProcessor.MYSQL)`
使用的是同一对构造参数，**除新增 `prepareAuth` 覆写外行为完全等价**，引号包裹与 LIMIT 分页无差异。
另确认：全仓再无第二处 `registerDialect` 调用，与《动态切换数据库方案 / 多数据源》不存在方言注册互相覆盖的冲突。✅

残余约束（已在类注释声明）：仅覆盖 `DbType.MYSQL`。若切换 `DbType.OTHER`/PostgreSQL/DM 等，`prepareAuth` **不生效且无告警** → 需在接入其他库时同步注册对应方言（P2）。

### 3.3 循环依赖规避（`AdminDeptService` 不反向注入 Provider）

依赖方向取证：

```
AdminDataScopeProvider ──> AdminDeptService   (调 getDeptAndChildIds)
AdminDataScopeProvider ──> AdminPermissionService
AdminDataScopeProvider ──> SysAdminUserMapper
AdminDeptService       ──/─✗  AdminDataScopeProvider   (未注入，规避成环)
AdminUserService       ──> AdminDataScopeProvider   (叶子，不成环)
AdminRoleService       ──> AdminDataScopeProvider   (叶子，不成环)
```

`AdminDeptService` 若反向注入 Provider，将形成 `Provider → DeptService → Provider` 构造器循环，Spring Boot 4 默认禁止循环引用 → **启动直接失败**。当前设计把"部门变更后的缓存失效"降级为 TTL 到期重算，是唯一不破坏分层的选择，评价：**设计合理**✅。

代价与配套：R-4（部门变更 60s 陈旧）+ R-5（多实例不广播）。可选优化路径（不引入环）：
1. 在 `AdminDeptService` 发布 `DeptChangedEvent`，由 Provider 以 `@EventListener` 单向监听失效（推荐，仍是单向依赖）；
2. 或 Provider 改字段注入 + `@Lazy`（能启动但掩盖设计问题，不推荐）。

### 3.4 装配与线程安全

- `DataPermissionAspect` 用 `@annotation || @within` 双切点，`AnnotatedElementUtils.findMergedAnnotation` 方法优先、类兜底 → 类级注解 + 方法级 `enabled = false` 覆盖可正常工作 ✅
- `push/pop` 配对，`finally` 保证异常路径也弹出；空栈时 `IGNORE.remove()` 清理 ThreadLocal → 线程池无污染 ✅
- `ObjectProvider<DataScopeProvider>` 懒获取 → 方言 Bean 先于业务 Provider 创建也不报错 ✅

## 五、最小修复方案

用户要求"如有严重缺陷给出最小修复方案"——**存在 2 项 P0，以下为不改变架构的最小修复**。按用户既往偏好，**本轮未动业务代码，待确认后实施**。

### M-1：R-1（OR 短路）——无法在方言层根治，改以"约定 + API + 护栏"封死

已取证方言层不可行（`QueryWrapper` 不暴露 where 链，`bracket()` 与 `where(chain)` 均实测无效）。最小可行三步：

1. **`QueryWrapperX` 增加受控 OR API**（替代裸 `.or(...)`）：
   ```java
   /** 安全 OR 分组：整组括号包裹，可被 @DataPermission 追加条件正确 AND */
   public QueryWrapperX orGroup(QueryCondition condition) {
       return (QueryWrapperX) super.and(QueryMethods.bracket(condition));
   }
   ```
   实测渲染：`` WHERE `status` = 1 AND (`username` LIKE '%abc%' OR `mobile` = '138') AND `dept_id` IN (1, 2) `` ✅
2. **红线**：`@DataPermission` 方法内**禁止** `queryWrapper.or(...)` 顶层调用；OR 只能走 `orGroup(...)`。写入两份 checklist 与使用指南。
3. **护栏单测**：在 starter 新增 `DataPermissionDialectOrConditionTest`，用真实 mybatis-flex 渲染断言 `orGroup` 场景下过滤条件仍在括号外 AND 生效，并把危险写法固化为"已知不通过"的文档化用例。
4. 可选加固：向 mybatis-flex 提 issue，请求 `prepareAuth` 提供"整体重包裹"能力。

### M-2：R-2（byId 绕过）——Service 层显式归属校验

不改动框架，新增一个复用现有 SPI 的守卫工具，在写操作与详情入口显式调用：

```java
/** 行级权限的 byId 补漏守卫：BaseMapper 的 selectOneById/update/deleteById 不走 QueryWrapper，
 *  不受方言钩子保护，必须在 Service 层显式校验目标行的归属。 */
public final class DataScopeGuard {

    /** 校验当前用户对目标行的归属（dept 维度看 dept_id 是否在可见集合，self 维度看归属列） */
    public static void assertVisible(RowOwnership ownership) {
        DataScope scope = ownership.provider().getDataScope();
        if (scope == null || scope.getType() == DataScopeType.ALL) {
            return;                                   // 全部数据，直接放行
        }
        boolean ok = switch (scope.getType()) {
            case DEPT, DEPT_AND_CHILD, CUSTOM -> scope.getDeptIds().contains(ownership.deptId());
            case SELF -> Objects.equals(scope.getUserId(), ownership.ownerId());
            default -> false;
        };
        assertTrue(ok, SystemErrorCode.USER_NOT_FOUND, ownership.id());   // 复用 404 语义，不暴露存在性
    }
}
```

接入点（`AdminUserService` 6 处）：`getUser` / `updateUser` / `deleteUser` / `assignRoles` / `resetPassword` / `deleteUserBatch`（循环内自动覆盖）。
校验数据取自已查出的 entity，**零额外 SQL**；错误信息复用 `USER_NOT_FOUND`，与越权探测不泄露存在性。
成本：约 40 行新增 + 5 处 1 行调用 + 3~4 个单测。

### M-3：其余 P1 的最小处置（低成本，建议同批）

| 项 | 最小处置 |
| --- | --- |
| R-5 | 只改文档与 `AdminDataScopeProvider` 类注释：「单实例立即生效，多实例最迟 60s」 |
| R-4 | `AdminDeptService` 三处变更发 `DeptDataScopeChangedEvent`，`AdminDataScopeProvider` `@EventListener` 内 `invalidateAll()`（单向依赖，不成环） |
| F-2a | `process()` 超深度分支加 `log.warn`（一次性，可按 class 去重） |
| F-2c | 异常捕获下沉到单字段级，失败字段跳过并告警，避免整批 fail-open |
| F-2d / F-3 | 写入 checklist 红线（禁用 Map 下发敏感值；导出须显式过滤），暂不改代码 |
| F-4 | 待产品确认联盟/会员端是否纳管；若纳管则先改造 `PermissionChecker` 为会话路由 |
| 3.1 | 建议 `test` profile 开 `enabled: true`（需配套测试角色数据），否则集成层永远测不到本框架 |

### M-4：推广结论

- **列级（`@FieldPermission`）**：✅ **可推广到其他业务表**。机制、SQL 注册模板、前端 hook、17 例 starter 单测齐备，CLEAR/MASK 选型正确，通配符安全。唯一限制：**只推广到管理端口径的 VO**；会员端/小程序端 VO 须先完成 F-4 改造。建议首批：`AdminDeptVO.phone/email`、`AdminUserVO.realName`、`Oauth2ClientVO.clientSecret`（后者更应改为不下发）。
- **行级（`@DataPermission`）**：⚠️ **只读列表场景可推广**（`dept_id`/`create_by` 齐备 + 遵守 OR 红线即可）；**写操作与详情场景必须先落 M-2**，否则新模块会复制 R-2 的 IDOR。此外受"全库仅 `sys_admin_user` 有 `dept_id`"约束，部门维度推广前需先给业务表补 `dept_id`（DDL 变更），这是排期上的真实前置。
- **框架本体质量**：装配隔离、开关默认、ThreadLocal 生命周期、递归防护、异常兜底、方言等价性均取证通过，86 例测试全绿。框架**架构合格**，问题集中在"能力边界未被文档/护栏封死"（R-1/R-2）与"多实例时效表述"（R-5），而非实现粗糙。
