# 电商联盟推广系统一期建设方案（平台适配层 + 商品同步 + 转链）

> 上游文档：《电商联盟推广系统全栈建设指南》→《电商联盟推广系统业务深度分析》（一期章节）
> 设计时间：2026-08-15 ｜ 范围：`zhush-module-union` 一期（平台适配层 / 商品同步 / 转链 / 短链 / 点击追踪）
> 性质：**详细设计方案，代码暂不实现**。本方案描述"建什么、怎么建、接口契约是什么"，落地时按此实施。

## 一、一期范围与目标

### 1.1 目标

打通"**选品 → 分享**"主链路：商品能从第三方平台同步进来并缓存展示，推广者能对商品生成推广链接（长链/短链/口令/文案）并分享，点击行为可被记录（为二期归因打底）。

### 1.2 范围（做什么）

| 子域 | 内容 |
| --- | --- |
| 平台适配层 | `adapter` 包：SPI 接口 + 淘宝/京东/拼多多实现 + 大淘客备降实现 + API 调用日志切面 |
| 商品同步 | `ProductSyncJob` 定时任务（全量/增量/手动）、商品 upsert、同步日志、状态变更日志、三级缓存查询 |
| 转链 | 输入解析、平台推广链接生成、推广链接落库、短链生成/跳转、点击追踪、文案模板渲染 |

### 1.3 不做（留给后续期）

- 订单归因 / 订单同步 / 佣金计算（二期）
- 账户资金 / 提现 / 风控 / 外部推广者结算（三期）
- 用户端收益看板 / 团队报表 / WebSocket 通知（四期）

### 1.4 设计原则

1. **适配层只做协议转换**：平台差异全部收敛在 `adapter`，业务域只见 SPI 与统一 DTO
2. **幂等优先**：同步 upsert、转链复用均以唯一键/查询判重兜底
3. **写库异步化**：日志类（API 调用日志、点击明细）全部异步落库，不阻塞主链路
4. **复用现有资产**：44 张表、44 个 CRUD Service、QueryWrapperX、Converter、RedisCache、@Idempotent、starter-job 均直接复用，**一期不新增任何表**
5. **配置不进库**：平台密钥等走 `yml` + 配置类（一期不建平台配置表，避免 schema 变更）

## 二、总体设计

### 2.1 分层架构

```text
controller（admin / member / 短链跳转）
      │
      ▼
core（业务服务：商品查询、转链编排、短链、点击、文案模板）
      │                    │
      ▼                    ▼
adapter（平台 SPI + 各平台实现 + 调用日志切面）   mapper / entity（现有 44 表 CRUD）
      │
      ▼
job（ProductSyncJob，Quartz）  redis（RedisCache：缓存 + 分布式锁）
```

依赖方向单向：`controller → core → adapter / mapper`；`job → core`；`adapter` 不依赖任何业务服务。

## 三、平台适配层设计（adapter）

### 3.1 SPI 接口：`UnionPlatformClient`

```java
public interface UnionPlatformClient {

    /** 平台标识：UnionPlatformEnum */
    UnionPlatformEnum platform();

    /**
     * 选品搜索（分页拉取商品列表，全量/增量同步共用）
     * @param query 关键词/类目/价格区间/排序等
     * @param page  页码（从 1 开始）
     * @param pageSize 单页大小（平台上限内，建议 20~100）
     */
    ProductPageResult searchProducts(ProductSearchQuery query, int page, int pageSize);

    /** 商品详情（转链前校验 / 详情页兜底） */
    UnionProductDTO getProductDetail(String outerProductId);

    /**
     * 生成推广链接
     * @param req 商品/店铺/活动标识 + 推广位（adzone/position）
     */
    PromotionLinkResult createPromotionLink(PromotionLinkRequest req);

    /** 生成口令/二维码（淘宝 tkl、京东券口令等；平台不支持时返回 null） */
    PromotionCodeResult createPromotionCode(PromotionLinkRequest req);

    /** 平台是否可用（配置开关 + 健康检查） */
    boolean available();
}
```

> 订单查询类方法（getOrders）二期再加，本期 SPI 不预留空实现，避免接口膨胀。

### 3.2 统一 DTO

| DTO | 关键字段 | 说明 |
| --- | --- | --- |
| `UnionProductDTO` | platform、outerProductId、title、subTitle、imageUrl、imageList、marketPrice、salePrice、commissionRate、commissionAmount、shopName、shopId、categoryId、categoryName、salesVolume、couponId、couponAmount、couponStartTime、couponEndTime、detailUrl、brandName | 与 `union_product` + `union_product_extra` 字段一一对应，适配层负责**费率归一**（见下） |
| `ProductSearchQuery` | keyword、categoryId、priceMin、priceMax、sortBy（佣金/销量/价格）、platform | 各平台实现内部映射 |
| `ProductPageResult` | list、page、pageSize、total、hasMore | 分页统一形态 |
| `PromotionLinkRequest` | platform、linkType、outerProductId、shopId、activityId、platformAdzoneId、platformSiteId、promotionScene | 转链入参 |
| `PromotionLinkResult` | promotionUrl、promotionCode、qrCodeUrl、expireTime、platformExt | 转链出参 |
| `PromotionCodeResult` | code（淘口令等）、qrCodeUrl | 口令/二维码 |

### 3.3 费率归一规则（重要）

`union_product.commission_rate` 注释明确："佣金比率（平台原始值，淘宝为千分比需转换）"。适配层统一输出**百分比小数**（如 0.30 表示 30%），各平台实现内转换：

| 平台 | 原始形态 | 转换 |
| --- | --- | --- |
| 淘宝 | 千分比（如 300 = 30%） | ÷1000 |
| 京东 | 百分比（如 30） | ÷100 |
| 拼多多 | 百分比（如 30.00） | ÷100 |
| 大淘客 | 已是百分比字符串（如 "30.00"） | 解析后 ÷100 |

`commissionAmount` 预估佣金由适配层按 `salePrice × commissionRate`（已转换）计算填充，业务域不重复计算。

### 3.4 平台实现要点

**TaobaoPlatformClient（淘宝联盟）**

| 业务 | 官方 API（以最新文档为准） | 说明 |
| --- | --- | --- |
| 选品搜索 | `taobao.tbk.dg.material.optional.upgrade` | 物料搜索升级版，支持分页/排序/优惠券过滤 |
| 商品详情 | `taobao.tbk.item.info.get` | 单/批量商品信息 |
| 转链 | `taobao.tbk.privilege.get` | 需 pid + adzone_id/site_id |
| 口令 | `taobao.tbk.tpwd.create` | 生成淘口令 |

签名：TOP 协议 `appKey + timestamp + sign（MD5）`，注意**参数按 key 字典序拼接**、中文 UTF-8 编码；错误码 `isv.xxx` 统一映射 `PlatformApiException`。

**JdPlatformClient（京东联盟）**

| 业务 | 官方 API | 说明 |
| --- | --- | --- |
| 选品搜索 | `jd.union.open.goods.query` | 支持佣金/价格/类目过滤 |
| 商品详情 | `jd.union.open.goods.promotiongoodsinfo.query` | 推广商品详情 |
| 转链 | `jd.union.open.promotion.bysubunionid.get` 或 `jd.union.open.promotion.common.get` | 按推广位生成 |

签名：京东宙斯协议（SHA256 签名、时间戳、`v` 版本参数）；`outer_product_id` 为字符串（表注释已说明）。

**PddPlatformClient（多多进宝）**

| 业务 | 官方 API | 说明 |
| --- | --- | --- |
| 选品搜索 | `pdd.ddk.goods.search` | 多多进宝商品搜索 |
| 商品详情 | `pdd.ddk.goods.detail` | 商品详情 |
| 转链 | `pdd.ddk.goods.promotion.url.generate` | 需 pid（推广位） |

签名：MD5 + salt，`access_token` 走 oauth 流程（`pdd.ddk.oauth.goods.prom.url.generate` 需要时再对接）。

**DatokePlatformClient（大淘客备降）**

| 业务 | 聚合 API（以最新文档为准） | 说明 |
| --- | --- | --- |
| 选品搜索 | `/api/goods/get-goods-list` | 大淘客商品库 |
| 转链 | `/api/tb-service/get-privilege-link` | 淘宝转链聚合 |

**备降策略**：`PlatformClientFactory` 按 `zhush.union.platform.default-strategy` 路由——`official` 时各平台官方客户端优先，官方调用连续失败 N 次（如 3 次）且该平台存在聚合实现时自动降级；聚合平台无商品库时不做兜底（京东/拼多多官方失败直接报错，由同步任务重试）。

### 3.5 API 调用日志（union_api_call_log）

**`@PlatformApiLog` 注解**标注在平台客户端方法上，切面记录：

```text
platform（平台） | api_name（如 taobao.tbk.dg.material.optional.upgrade）
request_params（脱敏 JSON：密钥/token/口令原文替换为 ***）
response_code / response_msg | is_success | duration（耗时 ms）
```

实现要点：
- **脱敏**：参数序列化后对 `appKey/appSecret/sign/token/password/pid` 等 key 值打码
- **异步落库**：`ApiCallLogService` 通过独立线程池（如 `ExecutorService`，核心 2/最大 4）写入，失败仅日志告警不回滚业务
- **成功率监控**：`idx_is_success` 已建，后续 SBA/告警直接按失败率聚合

### 3.6 平台异常模型

`PlatformApiException` 字段：`platform`、`apiName`、`errorCode`、`errorMsg`、`retryable`（网络超时/限流=true；业务错误如商品不存在=false）。

- `retryable=true` → 同步任务记录 `sync_status=2` 并排入下轮重试
- `retryable=false` → 同步任务跳过该条，记入 fail_count 与 error_msg
- 全局异常处理（starter-web 已有）统一转换为 `Result` 错误返回

## 四、商品同步设计（sync + job）

### 4.1 任务定义

**ProductSyncJob extends AbstractJob**（`zhush.job.core.AbstractJob`，Quartz 上下文取参数）：

| 参数 | 说明 |
| --- | --- |
| `platform` | 目标平台（缺省=全部启用平台） |
| `syncType` | 1-全量 2-增量 3-手动 |

**注册方式**：`ProductSyncRegister`（`ApplicationRunner` 或 `@PostConstruct`）调用 `JobUtils.addCronJob(ProductSyncJob.class, "unionProductSync", "union", cron, params)`，cron 从 `zhush.union.sync` 配置读取：

```yaml
zhush:
  union:
    sync:
      incremental-cron: "0 */30 * * * ?"   # 增量：每 30 分钟
      full-cron: "0 0 3 ? * 1"            # 全量：每周一 03:00
      incremental-platforms: "1,2,3"      # 参与增量同步的平台
      full-platforms: "1,2,3"
```

**防重入**：任务入口用 `RedisCache.executeWithLock("union:sync:lock:" + platform, 1s, 10min, ...)`，同平台并发执行时直接跳过（记录日志），防止 Quartz 集群/手动触发叠加。

### 4.2 同步流程（ProductSyncService）

```text
1. 校验平台可用（zhush.union.platform.{p}.enabled && client.available()）
2. 创建 union_product_sync_log（status=0 进行中，start_time=now，sync_type）
3. 循环分页拉取 client.searchProducts（pageSize=100，hasMore 截止）
   3.1 逐条 upsertProduct（见 4.3）
   3.2 累计 success/fail
4. 更新 sync_log（status=1/2，end_time，total/success/fail，error_msg）
5. 清理失效商品：全量同步时，对"本次未出现在结果集且 last_sync_time < 本次开始时间"的
   该平台商品标记 status=2（下架），并写 union_product_status_log
```

**增量同步依据**：平台 API 的更新时间参数（淘宝 `start_time/end_time`、京东 `sortName=inOrderCount` 等按平台能力）+ 本地 `next_sync_time` 兜底；增量任务结束后更新 `next_sync_time = now + 30min`。

**分页边界**：单平台单次任务最多 50 页（5000 条）防任务超长；未同步完的剩余量在 sync_log.error_msg 中提示"存在未完成分页，下轮继续"，全量任务不受限。

### 4.3 商品 upsert（幂等核心）

```text
select by (platform, outer_product_id) [uk_platform_outer 唯一索引兜底]
├── 不存在 → insert（sync_status=1，status 按平台状态映射，last_sync_time=now）
└── 存在   → 比较敏感字段（sale_price、commission_rate、commission_amount、coupon_*、status）
             ├── 有变化 → update + 写 union_product_status_log（field_name=price/commission/status，
             │            old_value/new_value，operator_id 空=系统同步）
             └── 无变化 → 仅更新 last_sync_time
```

- **平台下架判定**：平台返回商品失效/已下架 → 本地 `status=2`
- **`union_product_extra` 写入**：搜索列表通常不含详情（desc/品牌/运费），一期策略：
  - 转链/详情页触发时懒加载 `getProductDetail` 并 upsert extra（`uk_product_id`）
  - 同步任务不做详情批量拉取（QPS 成本高），二期按需批量
- **类目映射**：`union_platform_category_map` 一期仅做**自动登记**（同步到的平台类目自动 upsert 映射行，`union_category_id` 留空待运营人工关联），不自动建 union_category

### 4.4 商品查询三级缓存（ProductQueryService）

**详情查询**（`/union/product/{id}` 与转链校验共用）：

```text
1. Redis：union:product:detail:{id}（TTL 30min + 随机 0~5min 防雪崩）
2. 未命中 → DB：union_product + union_product_extra（join 或二次查询）
3. DB 无 → 平台 API 兜底 getProductDetail（仅当商品存在 outer_product_id 且平台可用），
   成功则落库并回填缓存；失败返回"商品不存在"
```

**列表分页**（选品中心）：一期直接走 DB（`QueryWrapperX` 条件分页，条件：platform/status=1/keyword LIKE title/categoryId/sortBy 佣金|销量|价格），**不做列表缓存**（数据实时性要求高、条件组合多，缓存收益低）；热点搜索词可二期加 Redis ZSet 热搜。

**防穿透**：DB 无记录时缓存空值占位（`union:product:empty:{platform}:{outerId}`，TTL 5min），避免平台 API 被无效请求打爆。

**缓存失效**：同步 upsert 更新商品后主动 `delete("union:product:detail:{id}")`；上下架操作同样删 key。

### 4.5 手动触发与管理端接口

| 接口 | 说明 | 权限 |
| --- | --- | --- |
| `POST /admin/union/sync/product` | 手动触发同步，body：`{platform, syncType}`；返回 sync_log id | `union:sync:create` |
| `GET /admin/union/sync/log/page` | 同步历史（复用 `UnionProductSyncLogController` 已有 CRUD，无需新增） | `union:product-sync-log:query` |
| `POST /admin/union/product/{id}/status` | 人工上下架/推荐，body：`{status, isRecommend, remark}`；写 `union_product_status_log` + 删缓存 | `union:product:update` |

## 五、转链设计（link）

### 5.1 转链总流程（PromotionLinkService）

```text
输入（sourceType + sourceInput）
  │
  ▼
LinkSourceParser 解析（见 5.2）→ 平台 + 目标（outer_product_id / shopId / keyword）
  │
  ▼
商品准备：outer_product_id 存在 → 校验/懒加载商品详情并落库（auto_save_product=true 时）
  │
  ▼
转链配置匹配：union_link_config（member_level / platform / category_id，priority 排序取第一条）
  │
  ▼
调平台 createPromotionLink（Factory 路由，失败→备降）→ PromotionLinkResult
  │
  ▼
落 union_promotion_link（幂等复用规则见 5.3）
  │
  ▼
按配置：enable_short_url → ShortUrlService 生成短链；enable_promotion_code → 口令
  │
  ▼
渲染文案（PromotionTemplateService）→ 组装 UnionPromotionLinkVO 返回
  │
  ▼
写 union_link_request_log（result_status=1/2/3，api_call_duration、total_duration、error 信息）
```

### 5.2 输入解析（LinkSourceParser）

| sourceType | 输入示例 | 解析逻辑 |
| --- | --- | --- |
| 1-商品链接 | `https://item.taobao.com/item.htm?id=123&xxx` | URL 域名识别平台 → 提取 `id`/`skuId`/`goods_id` 参数 |
| 2-商品ID | `1234567890` + platform 参数 | 直接使用 |
| 3-淘口令 | `￥abc123￥` / `₤xxx₤` | 正则提取口令 → 调用平台口令解析 API（淘宝 `taobao.tbk.tpwd.parse`，一期若平台无解析 API 则直接透传口令给用户，提示"请复制口令到 App 打开"） |
| 4-搜索关键词 | `连衣裙 夏` | 走选品搜索取第一条商品转链（返回结果需用户确认时改由前端先搜索再转链，一期支持"关键词转链=搜索 top1"） |

解析失败 → `link_request_log.result_status=2` + `SOURCE_PARSE_FAILED` 错误码，前端提示"无法识别的链接"。

### 5.3 推广链接落库与幂等

`union_promotion_link` 写入：memberId、promoterType（当前登录端身份）、platform、platformAdzoneId/siteId（淘宝从配置取）、productId、shopId、linkType、promotionUrl、promotionCode、expireTime（按 `union_link_config.expire_strategy`：activity 7 天 / product 30 天 / shop 60 天 / default 30 天）、status=1。

**复用规则**：同 `(member_id, platform, product_id, link_type)` 存在 `status=1` 且未过期的链接 → 直接复用并返回（不重复调平台 API）；不存在或已过期 → 新建。店铺/活动/通用类型按 `(member_id, platform, shop_id/activity_id, link_type)` 同理。

> 说明：平台推广链接通常**长期有效**（链接本身无过期），`expire_time` 是业务侧"重新生成"的触发点；过期仅标记 `status=2`，不物理删除，历史点击/归因数据不失效。

### 5.4 短链服务（ShortUrlService）

**算法选型：自增 ID + 62 进制编码**（推荐）

- `shortCode = base62(union_short_url_map.id)`，如 id=10086 → `q0e`（6 位内可容纳 56 亿条）
- 优点：无碰撞、可逆、可预估长度；不依赖哈希与查重
- 生成流程：先 insert 映射行拿到自增 id → 编码 code → update 回填（或 insert 前用 Redis INCR 预取 id，一次写入完成）
- **并发安全**：`RedisCache.increment("union:short:seq")` 预取 ID 区间，本地分配，避免 DB 自增锁竞争；DB 唯一索引 `uk_short_code` 兜底

**映射表写入**（`union_short_url_map`）：shortCode、promotionLinkId、originalUrl（平台推广长链）、targetUrl（= originalUrl，一期不做 A/B）、expireTime（来自 promotion_link）、status=1、totalClicks=0。

**Redis 缓存**：`union:short:{code}` → `{promotionLinkId, targetUrl}`，TTL = 链接过期时间（最长 7 天），保证跳转接口读缓存即可完成 99% 请求。

### 5.5 跳转与点击追踪

**跳转接口**：`GET /s/{code}`（`@IgnoreAuth`，全量公开，不需要登录）：

```text
1. 查映射：Redis（union:short:{code}）→ 未命中查 DB → 均无 → 404（SHORT_URL_NOT_FOUND）
2. 校验：status=1 且未过期，否则 410（SHORT_URL_EXPIRED / LINK_DISABLED）
3. 记录点击：构造 UnionClickTracking 事件（见下）→ 异步入队
4. 302 重定向到 targetUrl（携带渠道参数 ?u_code=xxx 便于二期归因对账）
```

**点击记录（ClickTrackingService）**，对应 `union_click_tracking` 字段：

| 字段 | 来源 |
| --- | --- |
| shortCode / promotionLinkId / memberId / platform / productId | 映射表 + 推广链接 |
| userId | Sa-Token `StpLogic(member)` 登录态（未登录 null） |
| visitorId | Cookie `union_visitor_id`（首次访问生成 UUID，HttpOnly，7 天）；前端可显式传 `visitor_id` 参数覆盖 |
| clickIp / userAgent / referer | `HttpServletRequest` |
| province / city | `starter-biz-ip`（ip2region 查 clickIp，异步执行） |
| clickTime | 事件时间 |

**异步落库策略**（一期不引入 MQ，使用内存线程池）：

- `ClickTrackingService` 持有独立线程池（核心 4 / 最大 8 / 队列 10_000，满了丢弃并计数告警日志）
- 明细异步 insert；`short_url_map.total_clicks`、`last_click_time` 异步累加更新
- `unique_clicks` 去重：Redis Set `union:short:uv:{code}:{yyyyMMdd}` 存 visitorId，`sAdd` 返回 1 时表示新访客（一期在异步任务中批量判断；Set 过期 48h）
- **崩溃容忍**：明细丢失可接受（仅统计损失），归因二期再引入"点击先落 Redis 再定时批量刷库"的可靠方案

> 设计取舍说明：点击链路一期以"低延迟、不阻塞跳转"为第一目标；可靠性与归因强一致在二期随 MQ 一起落地（分析文档链路 2 已注明）。

### 5.6 文案模板（PromotionTemplateService）

- 模板匹配：`template_type=1`（文案）中按 `(platform, category_id)` 精确匹配 → `platform` 匹配 → 通用模板（`platform/category_id` 为 NULL），priority 排序取最优
- 变量替换：`{title}`、`{price}`、`{commission}`、`{shortUrl}`、`{code}`（口令）、`{shopName}`、`{platformName}`；缺变量值则替换为空串
- 输出：`copyText`（标题模板 + 描述模板拼接），供前端一键复制；海报（template_type=2）一期仅返回底图 URL 与 `image_config`，**海报合成（画图）不在一期**（无图片处理服务，四期评估）
