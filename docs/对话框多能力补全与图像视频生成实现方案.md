# 对话框多能力补全与图像/视频生成实现方案（P0·P1·P3·P4·P5）

> 承接《对话框自然语言多能力任务实现方案.md》与其第十一节落地对账：本期补齐 **P0 遗留缺陷**（taskType 上下文、文案模式）、**P1 未接的前端导出**、**P5 配额与合规**、**P3 图像生成**、**P4 视频生成**。
> 已确认的决策基线：① 可插拔 SPI + 一期只实现 DashScope；② 异步结果用**前端轮询新接口**；③ 配额**按人按日/月次数 + 管理员豁免**；④ 先方案后代码，编码顺序 **P0 → P1 → P5 → P3 → P4**。
> 本文所有前提均为 2026-09-23 代码/字节码/离线仓库取证结果，不含推测。

## 一、底座改造（P3/P4/P5 共同前提，编码顺序第 0 步）

### B1｜把 AgentContext 注入到工具方法（starter-agentscope）

1. `DefaultAgentTemplate.runtimeContext(def, sessionId, ctx)`：build 后追加 `rc.put(AgentContext.class, ctx);`（F7 的实例方法）。
2. `ReflectiveAgentTool`：
   - `paramsSchema()` **跳过**类型为 `AgentContext` 的参数（不告诉 LLM、不让它填）；
   - `invoke(Map input, ToolCallParam param)`：该参数改由 `param.getRuntimeContext().get(AgentContext.class)` 注入，取不到时回退 `AgentContext.builder().userId(0L).userType("admin")`；
   - 为此 `callAsync` 调 `invoke(param)` 而非 `invoke(param.getInput())`（F9）。
3. 不新增 `AgentContextHolder`（跨线程不可靠，且 F7 已给原生通道）。
4. 单测：`ReflectiveAgentToolContextInjectionTest` —— 断言 schema 不含 `AgentContext` 参数、注入值正确、缺 RuntimeContext 时走兜底。

> 这一改造同时服务：P5 配额（要 userId/userType）、P3/P4（任务归属与产物隔离）、审计 `user_type` 修正。

### B2｜产物落 `infra_file`（starter-file + module-system + module-ai）

1. `starter-file` 新增 SPI：`com.zhush.file.core.FileRecordStore`
   ```java
   public interface FileRecordStore {
       FileUploadResult upload(byte[] content, String fileName, String contentType, String userType);
   }
   ```
   语义 = 「上传 + 落 `infra_file` + 返回带 id 的结果」；`FileUploadResult` 增 `Long id`（可为 null）。
2. `starter-file` 提供 `NoopFileRecordStore`（仅委托 `FileClient.upload`）并用 `@ConditionalOnMissingBean` 兜底；`module-system` 新增 `InfraFileRecordStore implements FileRecordStore`（复用 `FileService` 的落库逻辑，`storageType/creator/userType` 一致），`@Primary` 覆盖。
3. `AgentDocumentService` 与 P3/P4 的转存统一注入 `FileRecordStore`（不再直连 `FileClient`）→ 关闭 05 文档 🟡「产物不入库、无清理入口」缺口。
4. `FileService.uploadFile(MultipartFile,...)` 的重复落库代码抽公共方法，两处共用一条 insert 路径。

### B3｜统一任务类型与常量

- 新增枚举 `com.zhush.ai.enums.AiTaskType`：`chat / copywriting / docx / pdf / parse / image / video`，含 `of(String)` 容错（未知 → `chat`）。
- 它是 **taskType（前端意图/配额维度）**，与 `ai_model.capability`（text/image/video/audio，模型能力）**两套语义、不可混用**；映射表：`chat/copywriting/docx/pdf/parse → text`，`image → image`，`video → video`。

## 二、P0：意图路由基础补全

### 2.1 taskType 全链路

| 层 | 改动 |
|---|---|
| DB | `sql/26`：`ALTER TABLE ai_chat_message ADD COLUMN task_type VARCHAR(16) NOT NULL DEFAULT 'chat' COMMENT '任务类型…' AFTER attachments;` |
| 后端入参 | `AgentChatParam` 增 `String taskType`；`AgentChatService.stream/chat` 解析为 `AiTaskType`（非法值 → `chat`），随 `saveMessage` 落库 |
| 后端出参 | `AiChatMessageVO` 增 `taskType`；`AiSessionQuery` 增 `taskType` 过滤（可选） |
| 事件 | 复用现有 `session` 事件旁路：`AgentStartedEvent` 不带 taskType（避免动 starter 事件契约），前端本地持有即可 |
| 前端 | `ChatMessage` 增 `taskType?: string`；`send()` 时把当前 capability 映射的 taskType 一并存入本地消息与请求体；`api/ai/session.ts` 的 VO 类型同步 |
| 能力选项 | `ASSISTANT_CAPABILITIES` 每项补 `taskType` 字段（`auto→chat`），消除「instruction 里藏意图、结构上不可判」的问题 |

**用途闭合验收**：① 埋点——`ai_usage_record.task_type` 可按类型统计（§四）；② 配额——按 task_type 限次（§四）；③ UI——历史消息按 taskType 显示产物类型徽标。三项都必须能从数据里读出来，不接受「字段加了但没人用」。

### 2.2 文案模式

- 前端 `ASSISTANT_CAPABILITIES` 新增 `{ label: '文案生成', value: 'copywriting', taskType: 'copywriting', instruction: '请以营销文案方法论重写以下内容…' }`（插在 docx 之前）。
- 后端 `sql/26` seed 一条专用 Agent：`agent_definition` id `90004`、`name='ai-copywriter'`、`model='deepseek-chat'`、`tool_names='[]'`、`system_prompt`=文案方法论、`max_steps=3`、`group_code='common'`、`source=2`、`version=1`；同时 `sys_role_menu` 不需要新权限（复用 `ai:assistant`）。
- **决策**：`copywriting` 能力**只注入 instruction、不自动切 agent**（与 docx/pdf/parse 行为一致，避免隐式改会话归属）；用户想用专用 Agent 时从下拉里显式选 `ai-copywriter`。
- 顺带消灭死码：`AgentChatService` 入参校验接上 `MESSAGE_TOO_LONG`（阈值 `zhush.agentscope.chat.max-message-length:2000`）与 `CONVERSATION_LIMIT_EXCEED`（单用户活跃会话上限 `max-active-sessions:200`）。

## 四、P5：配额与合规（先于 P3/P4，因为是成本闸门）

### 4.1 表（`sql/27_ai_quota_generation.sql`）

```sql
-- 配额规则：按 user_type + task_type 限日/月次数；0 = 不限
CREATE TABLE ai_quota_rule (
  id BIGINT NOT NULL, user_type VARCHAR(16) NOT NULL DEFAULT 'member' COMMENT 'admin/member',
  task_type VARCHAR(16) NOT NULL DEFAULT 'chat' COMMENT 'chat/copywriting/docx/pdf/parse/image/video',
  daily_limit INT NOT NULL DEFAULT 0, monthly_limit INT NOT NULL DEFAULT 0,
  status TINYINT NOT NULL DEFAULT 1, remark VARCHAR(255) NOT NULL DEFAULT '',
  creator/create_time/updater/update_time/is_delete ..., PRIMARY KEY (id),
  UNIQUE KEY uk_type_task (user_type, task_type, is_delete)
);
-- 按人按日聚合用量（配额判定 + 成本可归人）
CREATE TABLE ai_usage_record (
  id BIGINT NOT NULL, usage_date DATE NOT NULL, user_id BIGINT NOT NULL, user_type VARCHAR(16) NOT NULL,
  task_type VARCHAR(16) NOT NULL DEFAULT 'chat', request_count INT NOT NULL DEFAULT 0,
  image_count INT NOT NULL DEFAULT 0, video_count INT NOT NULL DEFAULT 0,
  input_tokens BIGINT NOT NULL DEFAULT 0, output_tokens BIGINT NOT NULL DEFAULT 0,
  total_tokens BIGINT NOT NULL DEFAULT 0, cost DECIMAL(14,6) NOT NULL DEFAULT 0,
  ..., UNIQUE KEY uk_user_day_task (user_id, user_type, usage_date, task_type, is_delete)
);
```
Seed：`member` 的 `chat daily=100`、`image daily=10`、`video daily=2`、`docx/pdf/parse daily=50`；`admin` 全部 `daily_limit=0`（不限）。菜单 `3117` 配额管理（`/agent/quota`，权限 `agent:quota:list`）+ 按钮 `31171/31172/31173`（create/update/delete），`sys_role_menu` id `99024+`。

### 4.2 服务与接入点

- 新增 `AiQuotaService`（module-ai）：
  - `void assertAllowed(Long userId, String userType, AiTaskType taskType)`：`userType=admin` 或规则 `daily_limit=0` → 直接放行；否则 `SELECT` 当日/当月计数比对，超限抛 `AI_QUOTA_DAILY_EXCEED(1003501)` / `AI_QUOTA_MONTHLY_EXCEED(1003502)`；
  - `void record(...)`：**DB 原子自增**（照 `AgentUsageEventListener` 的「先 UPDATE，0 行则 INSERT，撞唯一键回退累加」写法，与既有并发口径一致），不引入 Redis 计数以保证可审计；
  - 规则走三级缓存刷新（复用 `dynamic-config` 的事件 + 定时兜底），改动后 `evictAllAgentCache` 不需要（配额不进 harness 缓存）。
- **限流**（QPS 维度，与「次数配额」正交）：新增 `AiRateLimiter`，基于 Redisson `RRateLimiter`（`RedisAutoConfiguration` 已暴露 `RedissonClient`，缺失时降级放行并 WARN），key `ai:rate:{userType}:{userId}`，默认 `10/min`（配置 `zhush.agentscope.quota.rate-per-minute:10`），超限抛 `AI_RATE_LIMITED(1003503)`。
- 接入点：`AgentChatService.stream/chat`（taskType 判定后）、`AgentExportController.export`、P3/P4 的 `generateImage/generateVideo` 工具与 `POST /task/submit`。`record` 在 FINISHED / 导出成功 / 生成任务 SUCCEEDED 三处调用（**失败不计数**，见风险 R3）。

### 4.3 合规强化

| 项 | 做法 |
|---|---|
| 生成工具纳入审批 | `generateVideo` 标 `@AgentTool(sensitive = true)`（高成本，走既有分级审批 + 路线 A 挂起）；`generateImage` **不标敏感**，由配额闸门控制（避免每张图都要人审） |
| 入参合规 | 新增 `ComplianceGuard.check(taskType, text)`：复用 `SensitiveWordResolver` 的 level 语义（1 提示 / 2 审批 / 3 拦截），对 `prompt`、导出 `content`、生成 `content` 生效；yaml 关键词回退保持存量语义 |
| 产物合规（一期不做视觉审核） | 明确记录为**未覆盖**：DashScope 侧自带内容审核（`inputChecks` builder 参数已在 F5 确认存在，一期透传），本仓库不接第三方图像审核 |
| 审计补齐 | `AgentAuditEventListener` 增 `AgentToolResultEvent` 分支写 `tool_result`（`truncateText(...,4000)` 已在事件侧做过）；`userType` 从 `AgentContext` 取（去掉硬编码 `"admin"`）；`TOOL_CALLED` 的 `arguments` 由事件补填并截断 |
| 归属与鉴权 | 见 §4.4，与配额同批交付 |

### 4.4 顺带关闭的 P0 安全缺口（配额生效的前提）

1. `AgentChatController`（9 接口）补 `@SaCheckPermission`：对话/会话类 → `ai:assistant`（菜单型）与 `ai:session:list`/`ai:session:delete`；`AgentDefinitionController` → `agent:definition:create/update/delete`；`AgentLogController` → `agent:log:list`；`AgentToolController` → `agent:tool:list`。均带 `type = CommonConstant.TYPE`，与既有 13 个已校验点写法一致。

## 五、P3：图像生成

### 5.1 SPI（`com.zhush.ai.generation.provider`）

```java
public interface GenerationProvider {
    String name();                                        // dashscope
    GenerationSubmitResult submit(GenerationRequest req); // 返回 remoteTaskId + status
    GenerationStatusResult fetch(GenerationCredential cred, String remoteTaskId, AiTaskType type);
```

- `GenerationRequest{type, model, apiKey, prompt, negativePrompt, size, n, duration, imageUrl, options}`；

### 5.2 模型解析（starter 薄改造，关闭 05 🟠 缺口）

### 5.4 后端链路

1. 工具 `AgentGenerationTools.generateImage`（`@AgentTool(name="generateImage", description="按文字生成图片…用户明确要出图/海报/插画时调用")`）：
   - 入参 `(String prompt, String size, Integer n, AgentContext ctx)` —— 最后一个参数由 B1 注入、不进 schema；
   - 顺序：`ComplianceGuard.check` → `AiQuotaService.assertAllowed(image)` → `resolveByCapability("image")` 取凭证（无启用模型 → `GENERATION_MODEL_UNAVAILABLE(1003601)`）→ 插 `ai_generation_task(status=0)` → 提交线程池执行 `asyncCall` → **立即返回** `{"ok":true,"taskId":"...","status":"submitted","hint":"图片生成中，稍后在产物卡片查看"}`（F9：返回 JSON String）；
   - 提交失败即置 `status=3` + `error_msg`，并返回 `{"ok":false,"error":...}`。
2. 转存与回填 `AiGenerationTaskService`：
   - 线程池（`ThreadPoolTaskExecutor`，2 线程、队列 50、线程名 `ai-generation-`，照 F12 先例）执行：`asyncCall` → 轮询 `fetch`（间隔 2s、上限 120s）→ SUCCEEDED 后下载 `url` 字节（复用 `AgentCapabilityTools` 的 SSRF 白名单校验抽成 `RemoteFileFetcher`，图像域名需允许 DashScope OSS 域，配置 `zhush.agentscope.generation.allowed-hosts`）→ `FileRecordStore.upload(...)`（B2，落 `infra_file`）→ 更新 task（`file_id/result_url/file_size/status=2/finish_time`）→ 把 `FileArtifact{type=image/video,format,url,size,name}` 追加进对应 `ai_chat_message.attachments`（按 `session_id` 找该会话最后一条 assistant 消息，`message_id=0` 时不回填）；
   - 兜底调度器：`ScheduledExecutorService` 每 15s 扫 `status IN (0,1)` 且 `submit_time < now-90s`（图像）/`< now-15min`（视频）的任务，主动 `fetch` 一次；超 `zhush.agentscope.generation.timeout-minutes`（图 5 / 视频 30）置 `status=4`（关闭 05 §九.2「悬挂任务」风险，前端未轮询也能收敛）。
3. 轮询接口：`AgentTaskController`（`/admin/ai/agent/task`）
   - `GET /{taskId}` → `Result<AiGenerationTaskVO>`（`status/statusText/url/size/name/errorMsg`），**必须 `assertTaskOwner`**（`task_id` + 当前 ctx 的 userId/userType）→ 非归属 `GENERATION_TASK_FORBIDDEN(1003602)`；权限点 `ai:assistant`；
   - `GET /page`（`AiGenerationTaskQuery`，管理端任务列表）→ `agent:task:list`（seed `3118`，按钮无需）。
4. 错误码（`AiErrorCode`，号段 F13）：`GENERATION_MODEL_UNAVAILABLE(1003601)`、`GENERATION_TASK_NOT_FOUND(1003603)`、`GENERATION_TASK_FORBIDDEN(1003602)`、`GENERATION_SUBMIT_FAIL(2003601)`、`GENERATION_FETCH_FAIL(2003602)`、`GENERATION_TRANSFER_FAIL(2003603)`；配额段 `AI_QUOTA_DAILY_EXCEED(1003501)`、`AI_QUOTA_MONTHLY_EXCEED(1003502)`、`AI_RATE_LIMITED(1003503)`、`SESSION_FORBIDDEN(1003504)`。

## 十、风险、不做项与后续

- **R1 SDK 传递依赖面**：`jsonschema-generator:4.31.1` 带入 `jackson-core/databind 2.21.4`（与项目 Jackson 3 `tools.jackson` 包名不同，可共存）；引入后必须跑全量 `test-compile` 确认无版本回退；若冲突则在 `zhush-dependencies` pin 并加 `<exclusions>`。
- **R2 供应商 URL 时效**：DashScope 返回的图片/视频 URL 有效期约 24h，**必须转存** `infra_file` 后才算交付（B2 是 P3 的硬前提，不可后置）。
- **R3 配额计数口径**：「失败不计数」对用户体验友好，但提交成功、转存失败的任务已消耗供应商额度 → 该类记 `status=3` 且**计入** `ai_usage_record.image_count`（成本归因优先），文案对用户仍提示可重试。
- **R4 单实例线程池**：生成任务线程池是本机内存态，多副本下轮询/兜底只在提交实例生效（与 05 §七 🟠「三处单实例内存态」同源）。一期接受，二期把「提交」与「轮询」解耦为 DB 驱动（兜底调度器扫全表 → 任一实例可接管），`ai_generation_task` 表已为此预留 `poll_count/submit_time`。
- **不做项（本期明确划出）**：① 产物视觉内容审核（依赖 DashScope `inputChecks` 透传）；② 多模态 embedding/RAG；③ C 端 `/member/ai/*`（单独一期，本期只做「admin/member 归属可区分」的地基）；④ WebSocket 推送（已选轮询）；⑤ 图生视频/首尾帧生视频（Builder 字段已确认支持，留 P4.1）。
