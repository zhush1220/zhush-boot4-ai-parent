# 数据权限页面化配置解决方案

> 目标：在**不改动核心框架、不重写权限体系**的前提下，把「行级 + 列级」数据权限的**资源定义与角色授权**尽量搬到管理端页面自助配置，覆盖"自定义部门权限控制""自定义行级/列级数据权限控制"三类诉求。
> 定位：解决方案设计（**暂不含代码实现**），供评审确认后再排期。
> 前置阅读：《[数据权限框架审计评估报告.md](./数据权限框架审计评估报告.md)》《[数据权限使用指南.md](./数据权限使用指南.md)》《[行级接入 checklist](./数据权限-行级业务表接入checklist.md)》《[列级接入 checklist](./数据权限-列级业务表接入checklist.md)》
> 配套原型：`docs/prototype/index.html`（单文件自包含，双击即可预览“数据资源管理”与“角色数据权限配置”两大页面）

## 一、现状边界（先讲清"已经能配什么"，避免重复造轮子）

| 维度 | 现状能力 | 配置入口 | 是否已页面化 |
| --- | --- | --- | --- |
| 行级·角色默认范围 | `sys_role.data_scope`（1全部/2本部门/3本部门及以下/4仅本人/5自定义） | 角色管理 →「数据权限」`data-scope.vue` → `assignRoleDataScope` | ✅ 已页面化 |
| 行级·自定义部门 | `data_scope=5` 时勾选部门集合落 `data_scope_dept_ids` | 同上（TreeSelect） | ✅ 已页面化 |
| 行级·按表分别设置 | ❌ 一个角色一套范围，作用于**所有**接入 `@DataPermission` 的表 | — | ❌ 缺口①|
| 行级·自定义条件 | ❌ 仅部门/本人，无"按业务字段条件"（如金额、状态、归属链路） | — | ❌ 缺口②|
| 列级·授权 | 权限点即 `sys_menu` type=3 按钮，勾菜单树即授权 | 角色管理 →「菜单权限」`menu.vue` → `assignRoleMenu` | ✅ 已页面化 |
| 列级·新增受控字段 | ❌ 需写 `@FieldPermission` 注解 + 手写 `sys_menu` 注册 SQL（如 31 号脚本）+ 发布 | 无 | ❌ 缺口③|
| 数据资源登记 | ❌ 哪些表/VO 纳入管控、`deptColumn`/`userColumn` 全靠代码注解硬编码 | 无 | ❌ 缺口④|

**结论**：授权的"最后一公里"（给角色勾选范围/字段）已可页面完成；**缺的是"资源与规则的定义"页面化**——即让超级管理员在页面上声明"某业务对象受控、其归属列是什么、有哪些敏感字段、默认策略如何"，并支持"按业务表分别设行级范围 + 自定义条件"。本方案聚焦补齐缺口①②③④。

### 现行框架与库结构取证引用（本方案依据）

> 以下均为已落地的现行代码/脚本事实（非设想），本方案所有改造点均据此推导。

**(1) 行级执行链路 — `DataPermissionDialect`**
路径：`zhush-framework/zhush-spring-boot-starter-biz-data-permission/src/main/java/com/zhush/data/permission/core/dialect/DataPermissionDialect.java`

- 继承 MyBatis-Flex 官方 `CommonsDialectImpl(KeywordWrap.BACK_QUOTE, LimitOffsetProcessor.MYSQL)`，重写数据权限扩展点 `prepareAuth(QueryWrapper, OperateType)`（:42）。
- 仅对 `SELECT/UPDATE/DELETE` 生效；仅当 `DataPermissionContextHolder.peek()` 非空且未 `isIgnored()` 时才追加（:47-50）。
- 解析期间 `setIgnore(true)` / `finally setIgnore(false)`，防止 provider 内部查库递归触发过滤（:57-62）。
- `buildCondition` 按 `DataScopeType` 分支（:75-81）：`ALL`→不追加；`SELF`→`userColumn = userId`；`DEPT/DEPT_AND_CHILD/CUSTOM`→`deptColumn IN (deptIds)`；`deptIds` 为空退化为 SELF（:96-101）；`userId` 缺失时 `denyAll()` 兜底 `= -1L` 不可见（:86-108）。
- **关键：过滤条件以 `queryWrapper.and(condition)` 追加（:68）**——这正是缺口②及审计 R-1（`OR` 优先级短路）要求"自定义条件必须 `QueryMethods.bracket` 整体包裹"的根因。

**(2) 数据范围 SPI — `DataScopeProvider` / `DataScopeType`**
- `@FunctionalInterface DataScopeProvider { DataScope getDataScope(); }`；未注册实现时框架不做过滤（`DataScopeProvider.java:14-23`）。
- `DataScopeType` 枚举五值：`ALL / DEPT_AND_CHILD / DEPT / SELF / CUSTOM`（`DataScopeType.java:8-24`），其中 `CUSTOM` 注释为"自定义部门范围"。
- 本方案新增的"按业务对象覆盖"与"自定义条件"即扩展到此 SPI 的资源维度重载，不改变既有五值语义。

**(3) 行级标注契约 — `@DataPermission`**（`.../annotation/DataPermission.java`）
- 属性：`enabled() default true`、`deptColumn() default "dept_id"`、`userColumn() default "create_by"`（:34-44）。
- 本方案登记表 `sys_data_resource.dept_column` / `user_column` 即**镜像**这两个属性；注解仍是"受控与否"的代码事实来源。

**(4) 管理端范围解析 — `AdminDataScopeProvider`**
路径：`zhush-module-system/src/main/java/com/zhush/system/security/AdminDataScopeProvider.java`

- `getDataScope()`（:74-90）：`StpAdminUtil.getLoginIdDefaultNull()` 为 null（未登录/定时任务）→ `DataScope.all()`（fail-open，对应审计 R-7）。
- `resolve()`（:122-164）：`hasAll = 超管编码 || dataScope == null || dataScope == 1`（:129-133）；多角色取并集，`2`→`userDeptId`、`3`→`deptService.getDeptAndChildIds(userDeptId)`、`5`→`parseDeptIds(role.getDataScopeDeptIds())`（:139-153）；无部门类范围→`DataScope.self(userId)`（:163）。
- 缓存：`CACHE_TTL_MILLIS = 60_000L`（:53）、`CACHE_PURGE_THRESHOLD = 512`（:58）、`invalidateAll()`（:98）/ `invalidate(userId)`（:105）。
- 由此确定：`sys_role.data_scope` / `data_scope_dept_ids` 正是本方案 `sys_role_data_resource` 的"**默认兜底层**"（资源未覆盖时沿用）。

**(5) 列级执行链路 — `FieldPermissionResponseAdvice`**
路径：`.../core/field/FieldPermissionResponseAdvice.java`

- 实现 `ResponseBodyAdvice`，`beforeBodyWrite` 内调 `process(body, 0)`，异常仅 `log.warn` 不阻断响应（:63-74）。
- `MAX_DEPTH = 4`（:40）；`ANNOTATED_FIELD_CACHE` / `NESTED_FIELD_CACHE` 为静态 `ConcurrentHashMap`（:45-50）。
- `process` 支持 `Result`/`PageResult`/`Collection` 及嵌套 VO；`isPlainType` 跳过 JDK 类型与 **`Map`**（:93）。
- `applyStrategy`（:121-131）：**primitive 字段跳过并保留原值**；`MASK` 仅对 `String` 生效（写 `maskValue()`），否则置 null。
- 判定来源 `permissionChecker.hasPermission(annotation.value())`（:99）——本方案列级授权**完全复用该权限标识口径**，故本链路**零改造**。

**(6) 列级标注契约 — `@FieldPermission`**（`.../annotation/FieldPermission.java`）
- 属性：`value()`（必填权限标识）、`strategy() default CLEAR`、`maskValue() default "***"`；`enum Strategy { CLEAR, MASK }`（:28-50）。
- 本方案 `sys_data_field.permission_code` / `default_strategy` / `mask_value` 即**镜像**此三属性。

**(7) 数据库结构 — `sys_role`**
- `sql/01_admin_rbac.sql:49`：`data_scope TINYINT NULL DEFAULT 1 COMMENT '数据权限：1-全部 2-本部门 3-本部门及以下 4-仅本人 5-自定义（预留）'`。
- `sql/04_dept_data_scope.sql:37-38`：`ALTER TABLE sys_role ADD COLUMN data_scope_dept_ids VARCHAR(1024) ... COMMENT '自定义数据范围的部门ID集合（逗号分隔，data_scope=5 时生效）'`。
- 二者为现网已在用的行级配置列，本方案**不修改其语义**，仅在其上叠加"按资源覆盖"。

**(8) 改造边界小结（对应第四章）**

| 框架 / 组件 | 现状 | 本方案动作 | 是否改运行期代码 |
| --- | --- | --- | --- |
| `DataPermissionDialect` | 按 `@DataPermission` 的 `deptColumn/userColumn` 统一过滤 | 增加"资源编码"入参，取资源级覆盖范围 / 自定义条件 | 是（增量，向后兼容） |

## 二、总体设计：三层配置模型

在不改变运行期框架（`DataPermissionDialect` 行级追加 SQL、`FieldPermissionResponseAdvice` 列级置空/脱敏）的前提下，新增"**配置元数据层**"，运行期改为"**注解 ∪ 动态配置**"的并集解析。

```
┌─ 数据资源层 sys_data_resource ────────────────────────────┐
│  声明"哪些业务对象纳入数据权限"：                              │
│  · 行级：受控表名 + 归属列(deptColumn/userColumn)            │
│  · 列级：VO 的敏感字段清单（自动扫描 @FieldPermission 登记）  │
└───────────────────────────────────────────────────────────┘
            │ 角色 × 资源
   ┌────────┴─────────┐
   ▼                  ▼
┌─ 行级规则层 ─────┐  ┌─ 列级字段层 ─────────────┐
│ sys_role_data_  │  │ sys_role_data_field      │
│ resource        │  │ 角色×字段：可见/脱敏策略   │
│ 角色×资源：范围  │  │ （替代手写 sys_menu SQL） │
│ +自定义条件      │  └──────────────────────────┘
└─────────────────┘
```

三张新表 + 两个已有落地页改造 + 一个元数据登记页。运行期 SPI（`AdminDataScopeProvider` / `AdminPermissionChecker`）改为读这三层配置，其余不动。

## 三、数据库设计

### 3.1 数据资源登记表 `sys_data_resource`

登记"可被数据权限管控的业务对象"。由后端**启动/手动触发扫描**自动初始化（反射扫描带 `@DataPermission` 的 Service 方法与带 `@FieldPermission` 的 VO），超级管理员可在页面微调。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `code` | varchar(64) | 资源编码，唯一，如 `system:user`、`union:withdraw-apply`（与列级权限点前缀同口径） |
| `name` | varchar(64) | 资源名称，如"管理员用户""提现申请" |
| `module` | varchar(32) | 所属模块 system/union/member/ai/pay |
| `table_name` | varchar(64) | 行级受控物理表名（无行级则空） |
| `dept_column` | varchar(64) | 部门归属列，默认 `dept_id` |
| `user_column` | varchar(64) | 数据归属人列，默认 `create_by` |
| `vo_class` | varchar(128) | 列级受控 VO 全类名（用于字段清单与运行期校验） |
| `row_enabled` | tinyint | 是否启用行级（0/1） |
| `field_enabled` | tinyint | 是否启用列级（0/1） |
| `status` | tinyint | 0停用/1启用 |
| 基础列 | — | `create_time/update_time/create_by/update_by/is_delete`（继承 `BaseEntity`） |

唯一键 `uk_code(code, is_delete)`。

### 3.2 数据字段登记表 `sys_data_field`（列级元数据）

把"哪些字段受控 + 默认策略"从**代码注解**镜像到**页面可管理的数据**，解决缺口③。字段仍保留 `@FieldPermission` 注解作为"代码事实来源"，本表是其**可运营副本**（登记/调整默认策略、显示名、脱敏文案），并自动同步一个 `sys_menu` type=3 权限点。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `resource_id` | bigint | → `sys_data_resource.id` |
| `field_path` | varchar(128) | VO 字段名/嵌套路径，如 `mobile`、`contact.phone` |
| `permission_code` | varchar(128) | 权限标识，如 `system:user:mobile`（与注解 value 一致） |
| `menu_id` | bigint | 自动登记的 `sys_menu` type=3 按钮 ID（授权仍走菜单树，避免双体系） |
| `label` | varchar(64) | 字段中文名，如"手机号" |
| `default_strategy` | tinyint | 无权限默认策略：1 CLEAR 置空 / 2 MASK 脱敏 |
| `mask_value` | varchar(32) | MASK 占位文案，默认 `***` |
| `status` | tinyint | 0/1 |

> **关键设计（对齐审计 F-4「全局单 `PermissionChecker`」）**：列级授权**仍复用 `sys_menu` + `sys_role_menu` 现有体系**（菜单树勾选已可用），`sys_data_field` 只是"字段元数据 + 自动建权限点"，**不引入独立的字段授权表**，避免权限判定出现两套口径。这样 `AdminPermissionChecker.hasPermission(code)` 无需改造，`FieldPermissionResponseAdvice` 也无需改造。

### 3.3 角色行级规则表 `sys_role_data_resource`（缺口①②）

`sys_role.data_scope` 作为**默认全局范围**保留；本表提供**"按资源覆盖"**与**"自定义条件"**。运行期解析优先级：资源级覆盖 > 角色默认 > 兜底仅本人。

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `role_id` | bigint | → `sys_role.id` |
| `resource_id` | bigint | → `sys_data_resource.id` |
| `scope_type` | tinyint | 1全部/2本部门/3本部门及以下/4仅本人/5自定义部门/**6自定义条件** |
| `dept_ids` | varchar(1024) | scope=5 的部门ID集合（逗号分隔，沿用现有 `data_scope_dept_ids` 格式） |
| `condition_json` | json | scope=6 的结构化条件（见 3.4） |
| 基础列 | — | `BaseEntity` |

唯一键 `uk_role_resource(role_id, resource_id, is_delete)`。

### 3.4 自定义条件 `condition_json` 结构（缺口②，安全核心）

**严禁存裸 SQL**（SQL 注入风险，且绕过方言层）。采用**字段白名单 + 操作符白名单 + 参数化值**的结构化表达式，后端据此构造 mybatis-flex `QueryCondition`：

```json
{
  "match": "AND",
  "rules": [
    { "field": "order_amount",  "op": "ge",       "value": 10000 },
    { "field": "order_status",  "op": "in",       "value": [2, 3] },
    { "field": "create_by",     "op": "eq_param", "value": "SELF" }
  ]
}
```

- `field`：必须在该资源登记的**可过滤列白名单**内（`sys_data_resource` 扩展一张 `sys_data_resource_field` 白名单表，或复用行级归属列 + 常用状态列），杜绝任意列名注入；
- `op`：白名单 `eq/ne/gt/ge/lt/le/in/nin/isNull/like`（`like` 强制参数化 `%value%`）；
- `eq_param:SELF` 等占位由运行期用当前登录主体替换，**不接受前端传入用户ID**（对齐审计 R-1 ID 空间红线）。

## 四、后端改造（复用框架，最小侵入）

### 4.1 元数据自动登记（缺口③④的根因治理）

新增一个**扫描器**（ApplicationRunner 或手动"同步元数据"按钮触发）：

- 反射扫描所有 `@DataPermission` 的 Service 方法 → 生成/更新 `sys_data_resource`（`table_name/dept_column/user_column` 取注解属性）；
- 反射扫描所有 VO 的 `@FieldPermission` 字段 → 生成/更新 `sys_data_field`，并对每个字段**幂等登记一个 `sys_menu` type=3 权限点**（把现在手写 31 号 SQL 的动作变成页面/系统自动完成）。

> 这样"新增一个受控列"的完整链路收敛为：**开发者只在 VO 加 `@FieldPermission` → 超级管理员点"同步数据资源" → 权限点自动出现在菜单树 → 页面勾选授权**。手写 SQL 环节消失。

### 4.2 行级解析改造 `AdminDataScopeProvider`

现状：只读 `sys_role.data_scope`。改为**按资源解析**：

- `DataScopeProvider` SPI 增加**资源维度**：新增方法 `DataScope getDataScope(String resourceCode)`（`getDataScope()` 保留为默认全局口径，向后兼容）。
- `DataPermissionDialect#prepareAuth`：从 `DataPermissionContextHolder` 取当前 `@DataPermission` 方法的资源编码（注解增加 `resource` 属性，或按 `table_name` 约定映射），调用带资源的重载；解析顺序：`sys_role_data_resource` 命中 → 否则角色默认 `data_scope` → 否则 SELF。
- `scope_type=6`：把 `condition_json` 编译成 `QueryCondition` 追加（走白名单校验）。
- **OR 短路红线不变**：条件一律以 `QueryMethods.bracket(...)` 整体括号后 AND（见行级 checklist 第 4 步）。

### 4.3 列级解析：零改造

列级判定 `AdminPermissionChecker.hasPermission(code)` 委托 Sa-Token 权限集合，权限集合来自 `sys_menu`——**页面勾选菜单即生效**，故 `FieldPermissionResponseAdvice`、`PermissionChecker` **无需改动**。`sys_data_field` 仅承担元数据与自动建权限点职责。

### 4.4 缓存失效补全

`sys_role_data_resource` 写操作后调用 `dataScopeProvider.invalidateAll()`（对齐审计 R-4/R-5：单实例立即、多实例最迟 60s，文档口径需注明）。

### 4.5 新增管理接口（REST）

| 接口 | 权限点 | 说明 |
| --- | --- | --- |
| `POST /admin/system/data-resource/sync` | `system:data-resource:sync` | 触发元数据扫描登记 |
| `GET /admin/system/data-resource/page` | `...:query` | 资源列表 |
| `PUT /admin/system/data-resource` | `...:update` | 启用/停用、改归属列、改默认策略 |
| `GET /admin/system/data-resource/{id}/fields` | `...:query` | 资源下受控字段清单 |
| `GET /admin/system/role/{roleId}/data-permission` | `system:role:assign-data-scope` | 聚合返回该角色的行级规则 + 列级已授权字段 |
| `PUT /admin/system/role/data-permission/row` | `system:role:assign-data-scope` | 保存 `sys_role_data_resource`（行级按资源） |
| `PUT /admin/system/role/data-permission/field` | `system:role:assign-menu`（复用）| 列级仍走 `assignRoleMenu` 勾选权限点 |

## 五、前端页面方案

### 5.1 新增「数据资源管理」页（超级管理员）

`views/system/data-resource/index.vue`：
- VxeGrid 列出资源（模块、名称、受控表、行级/列级启用状态）；
- 行操作：**同步元数据**（调 sync 接口）、**编辑**（弹窗切换 row/field 启用、改 `dept_column`/`user_column`、字段默认策略）；
- 展开行显示该资源的 `sys_data_field` 字段清单（只读，来源是注解扫描）。
- 路由挂到「系统管理」下，需新增菜单 + `system:data-resource:query` 权限点（这一条仍走标准菜单登记流程）。

### 5.2 改造「角色 → 数据权限」为两 Tab 弹窗

把现有单一 `data-scope.vue` 升级为 `data-permission.vue`（Tabs）：

- **Tab 行级**：
  - 顶部保留"默认数据范围"（= 现有 `data_scope` 5 选项 + 自定义部门 TreeSelect），维持兼容；
  - 下方"按业务对象精细化"表格：列出已启用行级的资源，每行可选 `沿用默认 / 覆盖范围(1-6) / 自定义条件`；
    - 选 `5` 出现部门 TreeSelect（复用现有交互）；
    - 选 `6` 出现**条件构造器**（字段下拉来自资源白名单、操作符下拉、值输入），落 `condition_json`。
- **Tab 列级**：
  - 列出各资源的受控字段，字段右侧开关 = 该角色是否拥有对应 `permission_code`；
  - 保存时转换为"菜单权限点勾选集合"调用 `assignRoleMenu`（**底层仍是菜单树授权，页面语义是字段授权**），避免维护两套角色-权限存储。

> 复用组件：部门 `TreeSelect`、`useVbenModal`、`TableAction`；权限码沿用 `system:role:assign-data-scope` / `system:role:assign-menu`，不新增列级授权权限点。

### 5.3 用户列表页现状保持

`views/system/user/index.vue` 的 `filterColumns` + `hasAccessByCodes` 列显隐机制不变——页面化配置只是改变了"权限点如何产生与授权"的方式，前端列显隐对配置来源无感知。

## 六、与审计结论的一致性校验（避免方案引入新缺陷）

| 审计缺陷 | 本方案的约束 |
| --- | --- |
| R-1 OR 短路 | 行级自定义条件一律 `QueryMethods.bracket` 括号后 AND；条件走白名单，不允许业务裸 OR |
| R-2 byId 越权 | **本方案不改变 byId 不受行级保护的事实**；页面配置的是"列表范围/列可见性"，详情/写操作仍需按行级 checklist 第 6 步显式归属校验（作为落地前置项一并排期） |
| R-4/R-5 缓存 | `sys_role_data_resource` 变更后 `invalidateAll()`；文档口径"单实例立即、多实例≤60s" |
| F-3 导出盲区 | 列级页面化不改变导出不经过 `ResponseBodyAdvice` 的事实；`sys_data_field` 增加 `has_export` 标记，导出链路据此手工过滤（单独排期） |
| F-4 全局单 Checker | 列级仍复用 `sys_menu` 权限集合 + 管理端 `AdminPermissionChecker`，**不新增第二套字段授权存储**，会员端门槛不变 |
| F-2 自定义条件注入 | `condition_json` 字段/操作符双白名单 + 参数化，禁裸 SQL；`SELF` 等主体值运行期注入不接收前端 ID |

## 七、分期实施建议（评审后排期）

**P0 前置（独立于本方案，须先做）**：修复审计 R-2（byId 归属校验）——否则即便列表范围配得再细，详情/写操作仍越权，页面化价值打折。

**阶段一（收益最大、改动最小）**：
- 列级页面自助登记：`sys_data_field` + 元数据同步（自动建 `sys_menu` 权限点）→ 消灭"新增受控列要手写 SQL"。
- 数据资源管理页（只读 + 启停 + 同步）。

**阶段二**：
- 行级"按资源覆盖"：`sys_role_data_resource`（scope 1-5）+ 角色数据权限两 Tab 弹窗。
- `AdminDataScopeProvider` 增加资源维度重载 + `DataPermissionDialect` 资源编码传递。

**阶段三（可选，风险最高）**：
- 行级"自定义条件" `scope=6` + 条件构造器 + 白名单编译。建议最后做，需专门做注入与性能评审。

## 八、方案取舍说明（为什么不选其他路线）

- **不为列级另建 `sys_role_data_field` 独立授权表**：会与 `sys_menu`/`sys_role_menu` 形成两套"角色能看什么"的存储，运行期 `PermissionChecker` 需同时查两处、且要处理冲突优先级，复杂且易漂移；复用菜单权限点模型改动最小、口径统一。
- **不把 `@FieldPermission`/`@DataPermission` 注解从代码移除改为纯 DB 驱动**：注解是"字段/方法受控"的代码事实来源，删除后 VO 与库表易失同步、且丧失编译期可见性；方案选择"注解为源、DB 为可运营副本、页面为授权与精细化"的折中。
- **自定义条件不用规则引擎/SpEL**：SpEL 有被执行任意代码的风险，且团队排错成本高；结构化白名单 JSON + 固定操作符编译足够覆盖"金额/状态/归属链路"常见诉求。
