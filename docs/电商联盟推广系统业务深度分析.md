# 电商联盟推广系统业务深度分析

> 分析对象：`zhush-boot4-parent`（Spring Boot 4.1.0 / Java 21 / MyBatis-Flex / Sa-Token / MySQL 8.0）
> 分析基线：《电商联盟推广系统全栈建设指南》（`docs/电商联盟推广系统全栈建设指南.md`）
> 分析时间：2026-08-15 ｜ 范围：`zhush-module-union` 全量代码 + `sql/` 脚本 + 基础设施 starter + 关联模块（member/pay/system）
> 结论性质：**分析结果文档，不含代码实现**

## 一、分析结论速览（TL;DR）

| 维度 | 结论 | 评级 |
| --- | --- | --- |
| 数据模型 | 44 张 union 业务表全部落地，字段设计比指南更完善（含 `sharding_key`、`calc_snapshot`、`confirm_status`、`settle_batch_no` 等增强） | ★★★★☆ |
| 代码骨架 | 44 Entity / 44 Mapper / 44 Service / 44 admin Controller 全套 CRUD 已生成，权限注解与菜单已补齐 | ★★★☆☆ |
| 核心业务逻辑 | **几乎为 0**：商品同步、转链、归因、佣金计算、账户入账、提现流转、风控执行全部缺失，系统当前不可用 | ★☆☆☆☆ |
| 用户端接口 | **完全缺失**：`controller/member` 目录为空，选品中心/转链工具/收益看板无任何接口 | ☆☆☆☆☆ |
| 基础设施 | job / mq / websocket / protection / file / excel / biz-ip 七大 starter 均有代码封装，但 union 未引入、配置默认关闭 | ★★★★☆ |

| 资金安全 | 账户并发更新、幂等去重、事务边界均停留在"设计"层面，无任何实现 | ☆☆☆☆☆ |
| 测试 | union 模块 0 测试 | ☆☆☆☆☆ |

**一句话结论**：联盟系统完成了"建表 + 生成式 CRUD"的第一阶段，数据模型质量较高、管理端骨架完整、基础设施就绪；但从"能跑 CRUD"到"可运营的推广系统"，核心业务链路（选品 → 转链 → 归因 → 结算 → 提现）尚有约 80% 工程量未开始，且资金与风控链路必须优先补齐才可上线。

## 四、核心业务链路深度分析（8 条链路）

> 每条链路给出：目标流程（指南）→ 现状 → 缺失环节 → 建设要点建议。代码不实现，仅定设计方向。

### 链路 1：商品选品与同步

**目标流程**：平台商品 API → 定时同步任务 → 商品主表/扩展表 → Redis 缓存 → 选品中心展示。实时查询三级兜底：Redis → 本地库 → 平台 API。

**现状**：`union_product` / `union_product_extra` / `union_product_category` / `union_category` / `union_platform_category_map` / `union_product_sync_log` / `union_product_status_log` 7 张表 + 7 个 CRUD Service。无同步任务、无平台客户端、无缓存读取、无分类映射同步。

**缺失环节**：
- 平台适配层（淘宝联盟 Tbk API / 京东联盟 / 拼多多多多进宝）——需新增 `adapter` 包，定义 `UnionPlatformClient` 接口 + 各平台实现 + 聚合平台（大淘客）备降实现
- 全量/增量同步任务（`AbstractJob` 子类，低峰期执行，增量优先、每周全量刷新）
- 商品查询三级缓存（Redis 优先，防击穿/穿透）
- 同步状态机（`sync_status` 0/1/2）与失败重试、状态变更日志

**建设要点**：先定义平台 SPI 接口与统一 DTO（商品、订单、链接），平台差异在适配层收敛；`union_api_call_log` 表已就绪，适配层每次调用必须落库（限流、对账、排查三用）。

### 链路 2：转链与短链

**目标流程**：选品 → 生成推广链接/口令/海报 → 短链接跳转追踪。三种推广方式：链接、口令（`promotion_code`）、海报（图片 URL）。

**现状**：`union_promotion_link` / `union_short_url_map` / `union_link_request_log` / `union_link_config` / `union_promotion_template` 5 张表 + CRUD。无转链生成、无短链算法、无跳转接口、无点击埋点。

**缺失环节**：
- 转链服务：调用平台推广链接 API（淘口令等）→ 落 `union_promotion_link`，`link_type` 支持单品/店铺/活动/通用
- 短链服务：ID 自增 + 62 进制编码（无碰撞、可逆）或 MD5 截断（需查重），映射表 `union_short_url_map`
- 跳转接口：`/s/{code}` 302 重定向，跳转前记录点击（IP/设备指纹/来源渠道）
- 点击明细异步落库：`union_click_tracking` 走 MQ 或异步线程池，避免高并发打爆主链路
- 文案模板：`union_promotion_template` 变量替换渲染分享文案

**建设要点**：短链 Key 需全局唯一索引 + Redis 缓存热链接；点击追踪是归因的数据底座，**点击记录必须先于订单归因建设**（归因需要 cookie/链接/设备指纹历史）。

### 链路 3：订单归因与同步

**目标流程**：平台推送/轮询 → 幂等去重 → 归因决策（Cookie / 推广链接 / 设备指纹 → 置信度评分）→ 落 `union_order` + `union_order_attribution_log` → 触发佣金计算。

**现状**：`union_order`（含 `order_source` 平台推送/定时轮询/手动录入、`parent_order_id` 合并支付、`promotion_link_id`、冗余商品字段）与 `union_order_attribution_log` 表结构**已超过指南设计**；无推送接收接口、无轮询任务、无归因写入方。

**缺失环节**：
- 平台推送 Webhook 接收接口（`@Idempotent` + `(platform, outer_order_id)` 唯一索引双保险）
- 定时轮询任务兜底（防丢单，`order_source=2` 标记来源）
- 归因决策器：优先精确匹配（用户登录态 + 推广链接）→ 次之 Cookie/短链码 → 最后设备指纹/模糊匹配，写入置信度；归因失败进入"待归因"池人工处理
- MQ 异步处理链：推送 → MQ → 消费（去重 → 归因 → 落单 → 触发佣金）

**建设要点**：**归因正确性决定佣金准确性**，置信度阈值与人工兜底流程必须在设计阶段定死；`parent_order_id`（合并支付拆单）场景要单独设计父子订单佣金拆分规则。

### 链路 4：佣金计算与分配（系统心脏）

**目标流程**：订单确认结算 → 规则匹配（`union_commission_rule` 按平台/类目/等级多维匹配，`priority` 优先）→ 多级分配（直推 + 上级 1~3 级，路径枚举 `union_member_relation.path`）→ 生成 `union_commission_record`（含 `calc_snapshot` 快照）+ `union_commission_distribution` 明细 → 状态机流转（待计算 → 待入账 → 已入账）→ 结算批次 `union_settle_batch`。

**现状**：`union_commission_rule` / `union_commission_record`（含 `calc_snapshot`、`confirm_status` 待确认/已确认/待修正、`settle_batch_no`、`retry_count`）/ `union_commission_distribution` / `union_commission_adjustment` / `union_settle_batch` 表结构完整；无规则匹配引擎、无计算逻辑、无状态机、无批次流转。

**缺失环节**：
- 规则匹配引擎：rule_type 全局/类目/等级/平台 + priority 排序 + 快照规则 ID
- 多级佣金拆分：沿 `path` 向上取 1~3 级，逐级按 `level_1_rate` 等比例计算，写入 distribution 明细
- 状态机：`status`（待计算→待入账→已入账）+ `confirm_status`（待确认→已确认→待修正），平台结算金额变动时走"待修正"重算而非直接改账
- 批次管理：每日/每周结算批次 `union_settle_batch`，批次内汇总入账，失败批次可重试（`retry_count`）
- 人工调整：`union_commission_adjustment` 调整单 → 触发重算或冲正，全程留痕

**建设要点**：`calc_snapshot` 存规则 ID + 各层级分配明细 JSON，是**对账与审计的唯一依据**，计算时必须序列化；佣金计算必须幂等（同一订单唯一 `uk_order_id`，重复计算返回已计算结果）。

### 链路 5：账户资金与流水

**目标流程**：佣金入账/提现冻结/退款回滚 → `union_member_account` 余额变更（`version` 乐观锁）→ 每笔变动写 `union_account_transaction`（`balance_before` / `balance_after`）。

**现状**：2 张表 + CRUD。无任何余额变动写入方；并发防护（`SELECT FOR UPDATE` + 乐观锁 + Redisson 锁）无代码实现。

**缺失环节**：
- 资金服务：统一入账/冻结/解冻/扣减 API，事务内"改余额 + 写流水"原子完成
- 并发控制：`FOR UPDATE` 行锁 + `version` 乐观锁（更新条件带 version，失败重试）+ 方法级 Redisson 锁兜底（key = memberId）
- 流水号生成：`transaction_no` 唯一键防重（幂等）
- 对账：日终任务核对"流水合计 == 余额"，偏差告警

**建设要点**：**这是全系统资金安全等级最高的一环**，必须流水与余额同事务、必须双重并发防护、必须可对账。指南第六部分 P0 问题 2 在此落地。

### 链路 6：提现审批与风控

**目标流程**：提交提现（校验 `union_withdraw_config` 最低额/次数/税费率）→ 风控检查（`union_risk_rule_config` 规则引擎评分 → 黑名单 `union_risk_blacklist` / 白名单 `union_withdraw_whitelist` / 自动审核 `union_auto_audit_config`）→ 审核（人工/自动，写 `union_withdraw_audit_log`）→ 冻结余额 → 打款（`zhush-module-pay`）→ 回调更新 → 冲正或重试。

**现状**：`union_withdraw_apply`（状态 1 待审核~6 打款失败 + `retry_count` + 打款渠道字段）/ `union_withdraw_config` / `union_withdraw_audit_log` / `union_withdraw_risk_record`（项目自增表，指南无）/ `union_withdraw_whitelist` / 风控 3 表齐全 + CRUD。无状态流转、无风控执行引擎、**`zhush-module-pay` 为 0 文件空模块，打款无落点**。

**缺失环节**：
- 风控引擎：`condition_expression` JSON 条件解析 → 匹配规则 → 决策（硬拒绝/转人工/降级/仅记录）+ `risk_score` 评分，执行上下文落 `union_risk_execution_log`
- 提现状态机：待审核 →（通过）→ 打款中 → 已打款 / 打款失败（重试）；审核与打款操作必须记录操作人
- 打款渠道：对接 pay 模块（BOM 已预留 WxJava 依赖），提现类型 1 银行卡/2 支付宝/3 微信；打款前冻结 `available_balance` → `frozen_balance`
- 回调与冲正：渠道异步回调 → 成功更新流水；失败转人工/重试（`retry_count` 上限）

**建设要点**：风控规则必须先于提现功能上线（提现是资金出口，规则缺失=裸奔）；自动审核阈值（`auto_audit_threshold`）与人工审核兜底结合，防止全额自动放行。

### 链路 7：外部推广者（影子账号）

**目标流程**：团长创建影子推广者（`union_external_promoter`，`bind_type` 临时/永久/活动）→ 独立账户体系（`union_external_account`）→ 佣金入"待结算池"（`union_external_commission_pending`，项目自增表）→ 团长手动结算或系统自动结算 → 提现（`union_external_withdraw`）。

**现状**：6 张表 + CRUD。无注册流程、无双轨结算逻辑、无影子账户资金操作。

**缺失环节**：
- 影子账号注册：`promoter_code` 唯一编码生成、`master_member_id` 归属绑定、有效期管理
- 结算双轨：`commission_settle_type=1` 团长手动确认 → 转正式佣金；`=2` 系统自动按规则结算；pending 池记录原始佣金与状态
- 独立资金流：外部账户入账/流水/提现与会员账户并行，但**共用一套资金操作规范**（乐观锁 + 流水）

**建设要点**：指南第六部分 P0 问题 1（`member_id` 与 `external_promoter_id` 互斥）在 `union_order` / `union_commission_record` 落库时强校验：`promoter_type=1` 只能有 `member_id`，`=2` 只能有 `external_promoter_id`。

### 链路 8：用户端与数据报表

**目标流程**（指南第五部分）：
- 用户端：选品中心（商品卡片/一键分享）、转链工具（链接/口令/海报）、收益看板（核心数据卡片/趋势图/订单明细）
- 管理端：仪表盘 KPI、推广者管理、商品管理、订单管理、财务对账、系统配置

**现状**：`controller/member` 空目录 → **用户端接口 0 个**；管理端为 44 个 CRUD 接口（可支撑列表页，无任何统计聚合接口）。`union_member_team_snapshot`（团队快照，项目自增表）与 `union_notification` / `union_member_device` 无写入方。

**缺失环节**：
- 用户端接口组：选品列表/详情（三级缓存）、转链提交、我的链接/点击/订单、收益汇总（今日/累计/待结算/可提现）、提现申请、消息列表
- 团队报表：按 `path` 前缀统计团队人数/订单/佣金（快照表支撑，避免实时递归）
- 通知推送：结算完成/提现结果走 `union_notification` + `starter-websocket`（`zhush.websocket.enabled=true` 后按 userId 推送）
- 管理端报表：仪表盘聚合（佣金支出/平台收入/推广者排行），可用 `starter-excel` 导出

## 五、关键设计议题（指南第六部分逐项落地建议）

| # | 议题 | 指南定级 | 落地建议 |

## 七、建设路线图建议（代码不实现，仅规划）

### 一期：数据底座与选品分享（打通"选品 → 分享"）

- **目标**：商品能从平台进来、用户能生成推广链接并分享
- **交付**：平台适配层（SPI + 淘宝/京东/拼多多实现 + 大淘客备降）、商品同步 Job（增量/全量）、商品三级缓存查询、转链服务、短链服务与跳转接口、点击追踪异步落库、`union_api_call_log` 接入
- **依赖**：starter-job（打开开关）、starter-redis（已有）、starter-protection（幂等）
- **验收**：选品列表可看、转链可生成短链、点击有明细、同步有日志

### 二期：订单归因与佣金（打通"下单 → 佣金"）

- **目标**：订单能进来、归因准确、佣金算得清
- **交付**：平台推送接收接口 + 轮询 Job、归因决策器（链接/Cookie/设备指纹 + 置信度）、MQ 消费链、佣金规则引擎、多级分配、`calc_snapshot` 快照、状态机流转、结算批次
- **依赖**：starter-mq（打开开关）、一期适配层（订单 API）
- **验收**：订单归因准确率达标、佣金计算可对账（快照回放一致）、重复推送不产生重复佣金

### 三期：资金与提现风控（打通"提现 → 到账"）

- **目标**：钱能安全地进来、审慎地出去
- **交付**：资金服务（锁 + 流水 + 乐观锁）、提现状态机、风控引擎、审核流、pay 模块打款渠道、外部推广者影子账号与双轨结算
- **依赖**：pay 模块启动、二期佣金入账
- **验收**：并发提现不超扣、流水余额对账为零差异、风控拦截命中可审计、打款失败可重试

### 四期：用户端与运营（打通"体验 → 增长"）

- **目标**：用户端可用、运营看得见
- **交付**：member 端接口组（选品/转链/收益看板/提现）、团队快照报表、WebSocket 通知、管理端仪表盘聚合、Excel 导出
- **依赖**：前三期全部完成
- **验收**：端到端跑通"选品 → 分享 → 下单 → 佣金 → 提现 → 通知"全闭环

## 九、附录：建议的新增代码结构（规划）

```text
zhush-module-union/src/main/java/com/zhush/union/
├── adapter/               # 平台适配层（一期新增）
│   ├── UnionPlatformClient.java        # SPI：商品/订单/转链统一接口
│   ├── taobao/TaobaoClient.java        # 淘宝联盟 Tbk API
│   ├── jd/JdClient.java                # 京东联盟 API
│   ├── pdd/PddClient.java              # 拼多多多多进宝 API
│   └── datoke/DatokeClient.java        # 大淘客聚合备降
├── job/                   # 定时任务（一期新增）
│   ├── ProductSyncJob.java             # 商品全量/增量同步
│   ├── OrderPollingJob.java            # 订单轮询兜底（二期）
│   └── SettleJob.java                  # 结算批次（三期）
├── mq/                    # MQ 消费（二期新增）
│   └── OrderPushConsumer.java          # 订单推送消费（去重→归因）
├── core/                  # 核心业务域（按链路分包）
│   ├── attribution/       # 归因决策器
│   ├── commission/        # 佣金计算引擎 + 状态机
│   ├── account/           # 资金服务（锁+流水）
│   ├── withdraw/          # 提现状态机
│   └── risk/              # 风控引擎
```
