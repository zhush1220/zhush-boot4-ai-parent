# 数据权限使用指南

> 模块:`zhush-spring-boot-starter-biz-data-permission`(框架层) + `zhush-module-system`(业务实现层)
>
> 能力:**行级权限**(SQL 自动追加过滤条件)+ **字段级权限**(响应字段置空/脱敏),支持五级自由启停。

---

## 一、功能总览

| 能力 | 实现方式 | 生效位置 |
| --- | --- | --- |
| 行级权限 | `@DataPermission` 注解 + MyBatis-Flex 方言 `prepareAuth` 钩子,按当前用户数据范围自动追加 `WHERE` 条件 | SELECT / UPDATE / DELETE(仅走 QueryWrapper 的 SQL) |
| 字段级权限 | `@FieldPermission` 注解 + `ResponseBodyAdvice`,无权限时字段置空(CLEAR)或脱敏(MASK) | 接口响应序列化前 |

数据范围类型(对应 `sys_role.data_scope`):

| 值 | 含义 | 追加的过滤条件 |
| --- | --- | --- |
| 1 | 全部 | 不过滤 |
| 2 | 本部门 | `dept_id IN (本部门)` |
| 3 | 本部门及以下 | `dept_id IN (本部门 + 全部子孙部门)` |
| 4 | 仅本人 | `create_by = 当前用户ID` |
| 5 | 自定义 | `dept_id IN (角色配置的部门ID集合)` |

多角色时取**并集**;部门集合为空时自动退化为"仅本人";未登录(定时任务等)不过滤。

## 二、启用与配置(五级启停)

### 1. 配置开关(application-{dev,prod,docker}.yaml)

```yaml
zhush:
  data-permission:
    enabled: true        # 总开关,默认 false(不启用,零开销)
    row-enabled: true    # 行级权限子开关,默认 true(受总开关约束)
    field-enabled: true  # 字段级权限子开关,默认 true(受总开关约束)
```

各 profile 现状:`dev` / `prod` / `docker` 已开启,`test` 保持关闭;开启前必须先执行
`sql/31_data_permission_activation.sql` 建好列级权限点,否则所有非超管角色的受控列直接返回空值。

### 2. 五级控制粒度

| 级别 | 方式 | 说明 |
| --- | --- | --- |
| 1 全局 | `zhush.data-permission.enabled` | `false` 时所有相关 Bean 不注册,零侵入 |
| 2 分类 | `row-enabled` / `field-enabled` | 单独关闭行级或字段级 |
| 3 注解 | `@DataPermission(enabled = false)` | 方法级覆盖类级注解,临时关闭 |
| 4 代码 | `DataPermissionHelper.ignore(...)` | 方法内某段逻辑跳过过滤 |
| 5 默认 | 不标注 `@DataPermission` | 未标注的方法完全不过滤 |

### 3. 模块接入(pom)

```xml
<dependency>
    <groupId>com.zhush</groupId>
    <artifactId>zhush-spring-boot-starter-biz-data-permission</artifactId>
</dependency>
```

`zhush-server` 与 `zhush-module-system` 已接入。

### 4. 数据库脚本

启用前需先执行 `sql/04_dept_data_scope.sql` 与 `sql/31_data_permission_activation.sql`:

- 新建 `sys_dept` 部门表(含根部门初始数据)
- `sys_role` 增加 `data_scope_dept_ids` 列(自定义范围的部门ID,逗号分隔)
- 业务表需有部门/用户归属列(默认 `dept_id`、`create_by`,可通过注解属性调整)
- 31 号脚本登记管理员敏感字段的列级权限点(`sys_menu` 按钮 + `sys_role_menu` 授权)

## 三、行级权限使用

> 完整可打勾版本见《[数据权限-行级业务表接入checklist.md](./数据权限-行级业务表接入checklist.md)》(含归属列 DDL 前置、OR 红线、`ignore()` 判定表、byId 越权补漏与缓存失效接入点)。

### 1. 基本用法

标注在 **Service 方法或类**上(也支持 Controller):

```java
// 方法级:该方法执行期间所有走 QueryWrapper 的 SQL 自动过滤
@DataPermission
public PageResult<OrderVO> getOrderPage(OrderQuery query) {
    return orderMapper.selectPageX(query, queryWrapper);
}

// 类级:整个 Service 生效,个别方法可关闭
@Service
@DataPermission
public class OrderService {

    @DataPermission(enabled = false)  // 该方法不过滤
    public OrderStatisticsVO statistics() { ... }
}
```

### 2. 自定义归属列名

表结构与默认列名不一致时:

```java
@DataPermission(deptColumn = "org_id", userColumn = "owner_id")
public List<ProjectVO> listProjects(ProjectQuery query) { ... }
```

### 3. 临时跳过过滤

`@DataPermission` 方法内部需查全量数据(统计、内部校验)时:

```java
@DataPermission
public OrderDetailVO getOrder(Long id) {
    OrderVO order = ...; // 已过滤

    // 这段查询不过滤
    long total = DataPermissionHelper.ignore(() -> orderMapper.selectCountByQuery(qw));
    ...
}
```

### 4. 生效边界(重要)

- **仅拦截走 QueryWrapper 构建的 SQL**(`selectListByQuery`、`selectOneByQuery`、`selectCountByQuery`、`selectPageX`、`deleteByQuery`、`update(entity, queryWrapper)` 等 `default` 方法)
- **不拦截**的调用(XML 原生 SQL、`@Select`、以及下列 byId 系列)不会追加过滤条件:

  ```
  javap com.mybatisflex.core.BaseMapper(1.11.8) 取证
  public abstract T   selectOneById(java.io.Serializable);   // 不经过 QueryWrapper
  public abstract int deleteById(java.io.Serializable);
  public abstract int update(T, boolean);                    // update(T) 委派至此
  public abstract List<T> selectListByIds(Collection);
  ```

  即 **详情、按 ID 的更新/删除不受行级保护**,必须在 Service 层显式校验归属,否则构成越权(IDOR)。见《数据权限-行级业务表接入checklist.md》第 6 步
- INSERT 不过滤
- 需要过滤的表必须有对应的归属列,否则 SQL 报"列不存在"错误
- 数据范围为"仅本人"但用户ID缺失时,追加 `= -1` 条件(拒绝所有数据,安全兜底)
- **OR 短路红线**:`prepareAuth` 以 `queryWrapper.and(cond)` 追加条件。业务 WHERE 含**顶层 OR** 时,MySQL 优先级 `AND > OR` 会使过滤条件只约束最后一个分支(实测:`... OR `mobile` = ? AND `dept_id` IN (...)` → 越权且无报错)。`QueryMethods.bracket()` 包裹追加条件、或把整条链交给 `where(...)` 均**实测不能修复**(方言层拿不到已有 WHERE 链)。唯一安全写法:顶层恒为 AND,OR 组自带括号 —— `.and(QueryMethods.bracket(a.or(b)))`

## 四、字段级权限使用

### 1. 基本用法

标注在**响应 VO 的字段**上,`value` 为权限标识(与菜单权限体系一致,由 Sa-Token 判定):

```java
@Data
public class AdminUserVO {

    /** 无权限者返回 null(默认策略 CLEAR) */
    @FieldPermission("system:user:mobile")
    @Schema(description = "手机号")
    private String mobile;

    /** 无权限者返回 *** */
    @FieldPermission(value = "union:promoter:bank-account",
                     strategy = FieldPermission.Strategy.MASK)
    @Schema(description = "银行账号")
    private String bankAccount;

    /** 自定义脱敏占位 */
    @FieldPermission(value = "member:user:id-card",
                     strategy = FieldPermission.Strategy.MASK,
                     maskValue = "保密")
    @Schema(description = "身份证号")
    private String idCard;
}
```

已接入的管理员字段(权限点登记在 `sql/31_data_permission_activation.sql`):

| VO 字段 | 权限标识 | 策略 | 选型原因 |
| --- | --- | --- | --- |
| `AdminUserVO.mobile` | `system:user:mobile` | CLEAR | 编辑表单会回填,脱敏值被提交会污染真实数据 |
| `AdminUserVO.email` | `system:user:email` | CLEAR | 同上 |
| `AdminUserVO.loginIp` | `system:user:login-ip` | CLEAR | 只读展示,置空后前端自动省略括号 |

### 2. 处理策略与选型

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| `CLEAR`(默认) | 字段输出 `null` | 字段会出现在**编辑表单**中 |
| `MASK` | String 字段输出 `maskValue`(默认 `***`);非 String 字段等同置空 | 仅列表/详情展示、不参与提交回写的字段 |

> 选 CLEAR 的前提是提交链路能过滤空值:MyBatis-Flex `update(entity)` 默认忽略 null 字段,前端表单需以
> `values.x || undefined` 提交(见 `views/system/user/modules/form.vue`),否则无权限者保存时会把真实值刷空。
> 反过来,若用 MASK,表单回填的 `***` 会被提交并写入数据库。

### 3. 生效边界

- 自动拆包 `Result` / `PageResult` / 集合 / 嵌套 VO(最大递归深度 4 层)
- 基本类型(`int` 等)字段无法置空,会跳过并打告警日志——**需要权限控制的字段请用包装类型**
- 判定口径来自**全局唯一的 `PermissionChecker` Bean**(当前为管理端 `AdminPermissionChecker`,内部先判 `StpAdminUtil.isLogin()`)
  - 只应对**管理端接口返回的 VO** 标注 `@FieldPermission`
  - 会员端/小程序端返回的 VO 若标注,会按管理端权限判定,会员会话下恒为无权限而把字段清空
  - 需分端控制时按端路由 `PermissionChecker`(见 FAQ Q7)
- 处理失败仅记录 warn 日志,不影响接口正常返回
- 给菜单表配置对应权限标识(如 `system:user:mobile`)并分配给角色,即可控制谁能看到该字段

### 4. 跨模块(后续业务表)接入清单

> 完整可打勾版本见《[数据权限-列级业务表接入checklist.md](./数据权限-列级业务表接入checklist.md)》(含 record/Map/导出等失效边界与会员端改造门槛),以下为要点摘要:

以「联盟推广员银行账号」新增一列受控字段为例,完整步骤:

1. **定权限标识**:按 `{模块}:{业务实体}:{字段}` 命名,实体取 kebab-case,与 `@SaCheckPermission` 同一口径,如 `union:promoter:bank-account`
2. **建权限点**:在 `sql/` 新增脚本(参 `31_data_permission_activation.sql`),向 `sys_menu` 插入 `type=3` 按钮并挂到该模块菜单下,同步 `sys_role_menu` 授权超管;主键 ID 先全库检索确认未被占用,脚本取幂等(先删后插)
3. **加注解**:在对应 VO 字段加 `@FieldPermission`,按上面「处理策略与选型」定 CLEAR/MASK,并在字段上方注释写明所需权限标识与选型原因
4. **模块 pom**:业务模块依赖 `zhush-spring-boot-starter-biz-data-permission`(仅为取注解类;Bean 装配由 `zhush-server` 统一完成,字段处理不依赖模块自身配置)
5. **前端隐列**:表格用 `#/hooks/use-field-permission` 的 `filterColumns`,列配置上加 `permission` 字段;非表格场景用 `canViewColumn('union:promoter:bank-account')`
6. **角色授权**:上线前为需要的角色勾选权限点(否则所有非超管角色的这些列立即变空)
7. **验证**:无权限角色调接口确认字段为 `null` 且列表不出现该列,有权限角色确认真实值与编辑回写不受影响

## 五、业务侧实现(system 模块)

框架通过两个 SPI 与业务解耦,system 模块已提供管理端实现(`com.zhush.system.security` 包):

### 1. AdminDataScopeProvider(数据范围解析)

解析流程:

```
未登录 ────────────────────────────→ 全部(不过滤)
   │
登录 → 查启用角色(sys_admin_user_role → sys_role)
   ├─ 无启用角色 ───────────────────→ 仅本人(最小权限)
   ├─ 超管(super_admin)/任一角色范围=1/未配置 → 全部
   ├─ 含部门类角色(2/3/5)→ 并集部门ID → dept_id IN (...)
   │    · 2:本人 deptId
   │    · 3:本人 deptId + 子孙部门(内存 BFS 展开)
   │    · 5:解析角色 data_scope_dept_ids
   └─ 全部角色均为 4 ────────────────→ 仅本人
```

- 解析结果按用户缓存 **60 秒**(每条 SQL 都会触发解析),并在以下变更时**主动失效**:
  `assignDataScope`(含角色启用状态变更)、`updateRole`、`deleteRole` 调 `invalidateAll()`;`updateUser`、`deleteUser`、`assignRoles` 调 `invalidate(userId)`
- 仅剩部门树本身变更(新增/改名/改父级)无主动失效,最迟 1 分钟后生效(避开与 `AdminDeptService` 的构造器循环依赖)
- **时效口径**:`invalidateAll()` 只清本进程缓存,**无跨实例广播**。单实例部署下上述变更立即生效;docker/prod 多副本下,未命中失效请求的节点最迟 60 秒生效
- 缓存超过 512 条目时整体清理,防止长期运行的内存泄漏
- 方言层调用 Provider 时已抑制递归,Provider 内部查库不会死循环

### 2. AdminPermissionChecker(字段权限判定)

委托 `StpAdminUtil.hasPermission(permission)`,未登录一律视为无权限。

超级管理员的权限列表为 `["*"]`,Sa-Token 的通配匹配会判定拥有任意权限标识(已实测),因此列级权限对超管无影响。

> 两者均为 `@Component`,自动替换 starter 的默认实现(默认实现为“全部数据 + 全放行”)。`PermissionChecker` 是**全局单 Bean**,
> 会员端如需自己的字段/数据权限,不能简单再加一个 `@Component`(会因 `@ConditionalOnMissingBean` 不生效且与现有实现冲突),
> 而应将现有 Checker 改造为按会话类型路由的实现。

## 六、角色数据范围配置

### 1. 配置接口

```
PUT /admin/system/role/assign-data-scope     权限标识:system:role:assign-data-scope
```

请求体:

```json
{
  "roleId": 2,
  "dataScope": 5,
  "dataScopeDeptIds": [10, 11, 12]
}
```

- `dataScope` 取值 1-5;仅为 5(自定义)时保存 `dataScopeDeptIds`,其余类型自动清空
- 自定义范围下 `dataScopeDeptIds` 不能为空(否则退化为“仅本人”),服务端报错 `1001104 自定义数据范围需至少选择一个部门`
- 前端传 ID 字符串数组(雪花ID 不走 Number 转换),后端去 null/去重后以逗号分隔落库,解析时还原为集合
- 角色详情/分页(`AdminRoleVO`)返回 `dataScope` 与 `dataScopeDeptIds`(逗号分隔字符串)

### 2. 部门管理接口

```
POST   /admin/system/dept          新增部门     system:dept:create
PUT    /admin/system/dept          修改部门     system:dept:update
DELETE /admin/system/dept/{id}     删除部门     system:dept:delete
GET    /admin/system/dept/{id}     部门详情     system:dept:query
GET    /admin/system/dept/list     部门列表     system:dept:query
GET    /admin/system/dept/tree     部门树       system:dept:query
```

约束:删除时不能存在子部门/部门下用户;父级不能设置为自身或其子孙部门;管理员通过 `sys_admin_user.dept_id` 归属部门。

## 七、常见问题(FAQ)

**Q1:开启后接口报"Unknown column 'dept_id'"?**
标注了 `@DataPermission` 的方法查询的表没有默认归属列。用注解属性指定实际列名,或该方法不加注解。

**Q2:为什么某个查询没有被过滤?**
依次检查:① 总开关/row-enabled 是否开启;② 方法或类上是否标注 `@DataPermission`;③ SQL 是否走 QueryWrapper(XML 原生 SQL 不拦截);④ 是否在 `DataPermissionHelper.ignore` 上下文中。

**Q3:调整了角色数据范围但没生效?**
角色数据范围/角色增删改/用户部门与角色变更都会主动失效缓存(单实例立即生效,多副本最迟 60 秒);只有部门树本身调整(新增/改名/改父级)仍依赖 60 秒 TTL,等待 1 分钟或重启服务。

**Q4:`@FieldPermission` 加在 `int` 字段上不生效?**
基本类型无法置空,改用包装类型(`Integer`/`Long` 等)。

**Q5:超级管理员会被过滤吗?**
不会。`super_admin` 角色编码或任一角色数据范围为"全部"时直接放行;角色 `data_scope` 为 NULL(存量数据)也视为全部。

**Q6:如何完全关闭数据权限?**
`zhush.data-permission.enabled: false`(默认值)。关闭后相关 Bean 不注册,无任何运行时开销。

**Q7:会员端(小程序)接口也能用 `@FieldPermission` 吗?**
不能直接用。字段判定走全局唯一的 `PermissionChecker`(当前为管理端口径),会员会话下 `StpAdminUtil.isLogin()` 为 false
→ 字段会被全部置空。需先改造 Checker 为按会话类型路由(管理端/会员端各自实现),再对会员端 VO 加注解。

**Q8:无权限角色看到列表里没有手机号/邮箱列?**
预期行为。后端已置空(`@FieldPermission` CLEAR),前端 `useFieldPermission().filterColumns` 会同步隐藏该列;
需要看到时给对应角色授予 `system:user:mobile` / `system:user:email` 权限点(菜单 ID 116/117)。

**Q9:列表加了 `@DataPermission`,但带关键字搜索时仍能看到别人的数据?**
优先怀疑 OR 短路(见上文「生效边界」)。搜索条件写成 `where(username like ?).or(mobile = ?)` 时,追加的 `dept_id IN (...)` 只约束 `mobile` 分支。改为 `.and(QueryMethods.bracket(username.like(?).or(mobile.eq(?))))`。

**Q10:为什么 `GET /admin/user/{id}` 能越权读到别人的记录?**
预期内的能力边界:`selectOneById`/`deleteById`/`update(entity)` 不构造 QueryWrapper,`prepareAuth` 拦截不到。列表安全 ≠ 单条安全,需在 Service 层显式校验归属(行级 checklist 第 6 步方案 A/B)。

**Q11:导出的 Excel 里为什么有明文手机号/IP?**
导出写 `HttpServletResponse` 输出流、返回 `void`,不经过 `ResponseBodyAdvice`,列级权限对导出无效。有 `/export` 的接口需在导出链路上手工做同一套字段判定,或从导出列中去掉。
