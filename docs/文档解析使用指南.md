# 文档解析使用指南

> 模块：`zhush-spring-boot-starter-file`（解析+上传）、`zhush-common`（Tika 工具类）、`zhush-module-system`（业务接入）
> 依赖：Apache Tika 3.3.1（tika-parsers-standard-package）

## 一、功能概述

提供"上传文档 → 提取内容 → 自动判图 → 图片上传文件服务 → 输出富文本"的一站式能力，
典型场景：**将 Word / PDF 文档内容转换后回显到富文本编辑器**（TinyMCE / wangEditor / Quill 等）。

完整流程：

```
POST /admin/system/file/parse-doc (MultipartFile)
  └─ FileService.parseDoc                    【zhush-module-system，事务】
       └─ DocParseService.parse              【starter-file】
            ├─ ① FileParseUtils.extractText     → Tika 提取纯文本
            ├─ ② FileParseUtils.extractImages   → 自动判断内容中是否存在图片
            ├─ ③ FileClient.upload(byte[])      → 有图片则逐张上传文件服务
            └─ ④ buildHtml                      → 文本包 <p> + 图片转 <img src='外链'>
       └─ 图片元信息落库 infra_file（可通过现有文件管理页查看/删除）
```

设计上的职责分层：

| 组件 | 模块 | 职责 |
|---|---|---|
| `FileParseUtils` | zhush-common | 纯静态解析工具（文本/图片/元数据/格式探测），不依赖 Spring、不做上传 |
| `DocParseService` | starter-file | 解析 + 判图 + 上传 + 富文本 HTML 组装（可注入 Bean） |
| `FileClient` | starter-file | 上传门面，支持 `MultipartFile` 与 `byte[]` 两种入参 |
| `FileService.parseDoc` | zhush-module-system | 业务入口，解析结果中的图片元信息落库 `infra_file` |

## 二、依赖与配置

### 2.1 Maven 依赖

业务模块（如 `zhush-module-system`）只需引入 `zhush-spring-boot-starter-file`：

```xml
<dependency>
    <groupId>com.zhush</groupId>
    <artifactId>zhush-spring-boot-starter-file</artifactId>
</dependency>
```

> `tika-parsers-standard-package`（含 POI / PDFBox）已由该 starter 显式声明，
> 使用方无需重复引入。仅使用 `zhush-common` 时因其为 `optional`，需自行声明。

### 2.2 配置项（`zhush.file.*`）

解析本身零配置；图片上传复用文件存储配置，关键项：

```yaml
zhush:
  file:
    enabled: true
    primary: local                       # local / aliyun-oss / qiniu / huawei-obs
    max-size: 52428800                   # 单文件上限 50MB（字节）
    # allowed-extensions: jpg,jpeg,png,gif,pdf,doc,docx   # 扩展名白名单，不配则不限制
    local:
      enabled: true
      base-path: D:/zhush/upload/
      domain: http://localhost:9166/files/
      url-path: /files/**
```

> **注意**：若配置了 `allowed-extensions` 白名单，必须包含 `png` / `jpg` / `gif`
> 等图片扩展名，否则文档中提取出的图片上传时会被拒绝（错误码见第七节）。

## 三、REST 接口

### 3.1 解析文档

| 项 | 内容 |
|---|---|
| 路径 | `POST /admin/system/file/parse-doc` |
| 权限 | `system:file:create`（Sa-Token，复用文件上传权限） |
| 幂等 | `@Idempotent(timeout=3)`，3 秒内防重复提交 |
| 入参 | `file`（form-data，文档文件） |
| 出参 | `Result<DocParseResult>` |

请求示例：

```bash
curl -X POST 'http://localhost:9166/admin/system/file/parse-doc' \
  -H 'Authorization: Bearer {token}' \
  -F 'file=@产品说明.docx'
```

响应示例（文档含图片）：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "fileName": "产品说明.docx",
    "hasImage": true,
    "text": "产品介绍第一行...",
    "html": "<p>产品介绍第一行...</p><p><img src='http://localhost:9166/files/2026/08/22/xxx.png' alt='image1.png' /></p>",
    "images": [
      {
        "fileName": "image1.png",
        "url": "http://localhost:9166/files/2026/08/22/xxx.png",
        "path": "2026/08/22/xxx.png",
        "storageType": "local",
        "contentType": "image/png",
        "size": 286
      }
    ]
  }
}
```

### 3.2 返回字段说明（DocParseResult）

| 字段 | 类型 | 说明 |
|---|---|---|
| `fileName` | String | 原始文档文件名 |
| `hasImage` | boolean | 文档内容中是否包含图片（自动探测） |
| `text` | String | 纯文本内容（不含标签，适用于摘要、全文索引） |
| `html` | String | 富文本 HTML：文本按段落包 `<p>`，图片以 `<img src='外链'>` 追加，可直接放入富文本编辑器 |
| `images` | List | 图片引用列表：`fileName`（文档内资源名）/ `url`（访问路径）/ `path`（存储相对路径）/ `storageType` / `contentType` / `size`，无图片时为空集合 |

## 四、前端富文本编辑器接入

后端返回的 `html` 字段中图片已是文件服务外链，前端直接回显即可：

```javascript
// wangEditor
import { createEditor, createToolbar } from '@wangeditor/editor-for-vue';
const res = await request.post('/admin/system/file/parse-doc', formData);
editor.setHtml(res.data.html);

// TinyMCE
tinymce.activeEditor.setContent(res.data.html);

// Quill
quill.clipboard.dangerouslyPasteHTML(res.data.html);
```

仅需纯文本（如生成摘要）时使用 `res.data.text`；需要单独管理图片时使用 `res.data.images`。

## 五、编程使用

### 5.1 注入 DocParseService（业务模块内）

`DocParseService` 已由 `FileAutoConfiguration` 自动装配，直接注入：

```java
@Service
@RequiredArgsConstructor
public class ArticleService {

    private final DocParseService docParseService;

    public void importFromWord(MultipartFile file) {
        DocParseResult result = docParseService.parse(file);
        // 支持三种入参：MultipartFile / InputStream / byte[]
        // DocParseResult r2 = docParseService.parse(inputStream, "xx.docx");

        if (result.isHasImage()) {
            // 图片已上传，result.getImages() 中为访问路径
        }
        String html = result.getHtml();   // 富文本
        String text = result.getText();   // 纯文本
    }
}
```

### 5.2 静态解析工具（不上传，仅提取）

`zhush-common` 提供 `FileParseUtils`，适合"只要内容、不要上传"的场景：

```java
// 文本提取（默认 10 万字符上限，可传 maxChars 调整）
String text = FileParseUtils.extractText(bytes);

// 图片提取（自动探测，无图片返回空集合）
List<ExtractedImage> images = FileParseUtils.extractImages(bytes);
images.forEach(img -> {
    img.getFileName();    // 文档内资源名（缺失时回退 image_N.ext）
    img.getContentType(); // 如 image/png
    img.getData();        // 图片字节
    img.toDataUri();      // data:image/png;base64,... （免上传，直接内嵌 HTML）
});

// 元数据 / 格式探测（基于内容而非扩展名）
Map<String, String> metadata = FileParseUtils.extractMetadata(file);
String contentType = FileParseUtils.detectContentType(file);
```

以上方法均支持 `InputStream` / `byte[]` / `File` 三种入参。

### 5.3 字节内容上传（图片等程序产生的文件）

`FileClient` 除 `MultipartFile` 外，提供字节内容上传重载：

```java
FileUploadResult result = fileClient.upload(bytes, "image1.png", "image/png");
// 指定存储平台：
// fileClient.upload(bytes, "image1.png", "image/png", "aliyun-oss");
result.getUrl();    // 访问 URL
result.getPath();   // 相对存储路径（删除定位用）
```

## 六、支持格式与解析说明

| 项 | 说明 |
|---|---|
| 支持格式 | Tika 全部可解析格式：docx / doc / pdf / txt / html / pptx / xlsx 等；**格式识别基于文件内容**，与扩展名无关 |
| 文本上限 | `extractText` 默认 100,000 字符（`FileParseUtils.DEFAULT_MAX_CHARS`），超限抛 `FILE_PARSE_ERROR`，可用带 `maxChars` 参数的重载调整 |
| PDF 内联图片 | 已通过 `PDFParserConfig.setExtractInlineImages(true)` 自动开启，无需额外配置 |
| 图片命名 | docx 内嵌图片名取自 OOXML 内部资源名（如 `image1.png`），**不一定等于**插入时的原始文件名 |
| 事务性 | `FileService.parseDoc` 带事务：图片落库失败会回滚数据库记录；但已上传的物理文件不会自动回滚（与项目普通上传行为一致） |

## 七、错误码

| 错误码 | 常量 | 触发场景 |
|---|---|---|
| 2000007 | `FILE_PARSE_ERROR` | 文档解析失败（格式损坏、文本超字符上限等） |
| 2000005 | `FILE_UPLOAD_ERROR` | 图片上传存储平台失败 |
| 2000006 | `FILE_STORAGE_ERROR` | 指定的存储平台未启用（`zhush.file` 配置错误） |
| 1000430 | `FILE_EMPTY` | 上传内容为空 |
| 1000413 | `PAYLOAD_TOO_LARGE` | 超过 `zhush.file.max-size` |
| 1000431 | `FILE_TYPE_UNSUPPORTED` | 扩展名不在白名单（配置白名单时未放行图片扩展名会在此报错） |

统一由 `GlobalExceptionHandler` 翻译为 `Result` 返回，前端按 `code != 0` 处理。

## 八、FAQ

**Q1：文档中的图片一定会上传吗？**
自动探测：无图片则跳过上传；有图片才逐张上传。`hasImage` 字段可用于前端展示"本文档含 N 张图片"。

**Q2：可以不上传、直接把图片内嵌到 HTML 里吗？**
可以。使用 `FileParseUtils.extractImages` + `ExtractedImage.toDataUri()` 得到
`data:image/png;base64,...` 形式的内嵌图片。注意 base64 会使体积膨胀约 33%，
大图片不建议，生产环境推荐走文件服务外链。

**Q3：解析出的原始文档本身会落库吗？**
不会。`parse-doc` 只对**提取出的图片**落库 `infra_file`；原始文档仅作为入参被解析。
如需同时保留原文档，先调 `POST /admin/system/file/upload` 再调 `parse-doc`。

**Q4：扫描版（图片型）PDF 能提取出文字吗？**
当前未集成 OCR，扫描版 PDF 只能提取出内嵌图片，文本为空。

**Q5：如何扩展新存储平台？**
实现 `FileStorage` 接口并注册为 Bean，配置 `zhush.file.primary` 指向其 `getType()` 即可，
解析上传链路自动生效，无需改动 `DocParseService`。
